    class nav_bar

    base widget : behavior, pointer_target · source

    nav_bar - the bar that switches between an app's tabs. Made with nav_bar(nav).

    column(modifier().fill()) {
    screens(nav, to_home(), modifier().grow(1)) {
        tab<to_home>("Home")       { home_screen(nav); };
        tab<to_library>("Library") { library_screen(nav); };
        screen<to_detail>()        { detail_screen(nav, it.id); };
    };
    nav_bar(nav);                               // under the screens: a bottom bar
}

    It shows one item per tab<...>(...) line of the screen list, in the order they are listed, and marks the tab that is showing. Clicking an item switches to that tab; clicking the tab that is already showing takes it back to its first screen.

    THE BAR HIDES WHILE A SCREEN IS OPEN ON TOP OF A TAB. A detail screen owns the whole window and has its own way back (top_bar); the tabs come back with the tab's first screen. Call .always() to keep the bar there throughout.

    Where the bar sits is up to you: put it after the screens for a bottom bar, before them for a top bar. (Android: BottomNavigationView. Compose: NavigationBar.)

    HOW IT WORKS: the bar is built AFTER screens(...) in the same build(), so the navigator's screen list is already written and the bar simply asks it: how many tabs, their words, which one is showing. It reads the navigator's state while it is made, so every move of the navigator rebuilds it - that is how it appears, disappears and moves its mark without being told.

    class navigator

    source

    navigator - where the app is: the screens that are open, and the ones underneath that "back" returns to.

    class my_app base composable {
    nav : navigator = navigator();
        override def build() : element {
        return column(modifier().fill()) {
            screens(nav, to_home(), modifier().grow(1)) {
                tab<to_home>("Home")       { home_screen(nav); };
                tab<to_library>("Library") { library_screen(nav); };
                screen<to_detail>()        { detail_screen(nav, it.id); };
            };
            nav_bar(nav);
        };
    }
}

    The screen list (screens.sharp) says what there is; the navigator says where you are. Screens are given the navigator and call it:

    nav.go(to_detail(7))        open a screen on top of the one showing
nav.show(to_player())       the same - unless that screen is already on top
                            (a double tap must not open it twice)
nav.back()                  return to the screen below
nav.back_to<to_home>()      return to the nearest screen of that kind below
nav.reset()         return to the first screen of this tab
nav.replace(to_login())     swap the top screen; back will not return to the old one
nav.current()               the route that is showing

    A screen does not need to know any other screen - only the route to it.

    TABS

    A screen written with tab<...>(...) is top-level: it is one of the places the tab bar (nav_bar.sharp) switches between. EACH TAB HAS ITS OWN BACK STACK. Open a detail screen in Library, switch to Home, switch back: the detail screen is still there, exactly as it was left. Going to a tab that is already showing returns it to its first screen.

    nav.go(...) with a tab's route switches to that tab; with any other route it opens that screen on top, in the tab you are in.

    "Back" on a tab's first screen returns to the FIRST tab - and from there has nowhere to go (back() gives 0).

    WHAT BACK KEEPS: a screen that is covered by another, or sits in a tab that is not showing, stays alive - its states, its scroll positions, its typed text - and is as it was left when it shows again. A screen that is popped off its stack is gone; opening it again makes a fresh one.

    (Compose: NavController + NavHost with typed routes, and the saveState / restoreState of bottom navigation. Android: fragments on back stacks. Here the bookkeeping those need - save, restore, launchSingleTop, popUpTo - is the default behaviour or one short word.)

    HOW IT WORKS

    kinds is the screen list: one entry per screen<...>() / tab<...>(...) line. It is written afresh every time the app's build() runs (the block of screens(...) runs again), so the functions in it always belong to the latest build.

    stacks holds the back stacks: one per tab, in the order the tabs are listed (an app without tabs just has the one). showing says which is in front. Each entry of a stack is one open screen: its route and its host - a small composable (screen_frame) that builds the screen by asking the screen list for the line that matches the route.

    Every move bumps a small state, moves. The widget that SHOWS the top screen (screens.sharp) and the tab bar read that state while they are built - so every move rebuilds them, like any other state change. last_move tells the showing widget which way to slide.

    Keep the navigator where it lives as long as the app: a field of the root composable. (A field of a nested composable is made anew whenever its parent rebuilds.)

    Fields

    listingnavigator?the navigator whose screen list is being written right now (screens(...) sets it while its block runs)
    last_move_int64which way the last move went: 1 forward (go), -1 back, 0 neither (a tab switch, replace, the first screen)

    class route

    source

    route - where the app can go. Every screen of an app has a route class that extends this one; the route's fields are what that screen needs.

    class to_home base route { }                    // a screen that needs nothing
    class to_detail base route {                    // a screen that needs to know which item
    id : _int64;
    to_detail(n: _int64) { id = n; }
}

    Going somewhere is making a route and handing it to the navigator:

    nav.go(to_detail(7));

    and the screen list (screens.sharp) says what is shown for each kind of route. The screen gets the route object back, so it reads its arguments as ordinary, typed fields (it.id) - there are no strings to parse and nothing to look up by name.

    WHY A BASE CLASS: the navigator only takes routes, and the screen list only registers screens for route classes. A route that is misspelt, or an object that is not a route at all, is caught by the compiler instead of showing up as a blank screen at run time. (Compose's typed navigation does the same with @Serializable route classes.)

    A route class is plain data: keep widgets and state out of it.

    class screen_host

    base widget : behavior, clipper, stateful · source

    screen_host - shows the top screen of a navigator, and animates the change when the navigator moves. Made with screens(...).

    screens(nav, to_home(), modifier().grow(1)) {
    tab<to_home>("Home")       { home_screen(nav); };
    tab<to_library>("Library") { library_screen(nav); };
    screen<to_detail>()        { detail_screen(nav, it.id); };
}.transition(TRANSITION_SLIDE)

    The block is the app's SCREEN LIST: one line per kind of route, saying what is shown for it. It is read into the navigator every time the app is built; which screen is actually showing is the navigator's business (navigator.sharp), and this widget shows it.

    THE TRANSITION

    When the navigator moves, whoever shows it is rebuilt (it read the navigator's state). The NEW screen_host finds that the top screen is not the one the OLD screen_host was showing - that is the moment a transition starts. It keeps the old screen as leaving and, for a fraction of a second, holds BOTH screens as children, placed side by side:

    forward (go)              back
+--------+--------+       +--------+--------+
| old <- | new <- |       | -> new | -> old |
+--------+--------+       +--------+--------+
the new screen comes      the old screen leaves the way it came,
in over the old one       uncovering the one below

    progress runs from 0 to 1 over the transition time. Each frame it is moved on by the time that passed, the two screens are arranged again at their new places, and another frame is asked for. At 1 the leaving screen is dropped and the host goes back to holding one child.

    The screen that is uncovered moves less than the one on top (a quarter of the way): that small difference is what makes it read as "underneath". The movement starts fast and settles gently (ease-out), which is how things that come to rest look.

    There is no transparency or scaling in the painter yet, so transitions are movements. A screen with no background of its own is painted on the theme's - a screen sliding over another must not be see-through.

    The host is a clipper (a sliding screen is cut off at the host's edges) and stateful (a rebuild in the middle of a transition carries the transition on instead of restarting it). (Compose: NavHost with enter / exit transitions. Android: fragment transactions with setCustomAnimations.)

    class typed_screen<t base route>

    : screen_kind · source

    One line of the screen list: "a route of type t is shown by this function". Made by screen<t>() { } and tab<t>(title) { }.

    It is generic so that the function gets the route AS ITS OWN TYPE (it.id is a real field of to_detail), while the navigator keeps all the lines in one list as plain screen_kind. where is t is what matches a route to its line.

    class typed_tab<t base route>

    : screen_kind · source

    A line of the screen list written with tab<t>(title) { }: a top-level screen, one of the places the tab bar switches between.

    A tab is opened by the tab bar, which has no route object to hand - so a tab makes its own (new t()). That is why A TAB'S ROUTE CLASS MUST BE MAKEABLE WITH NO ARGUMENTS: a tab is a place, not a particular item. (A route with arguments is for screen<...>(), which is always opened with a route someone made.)
