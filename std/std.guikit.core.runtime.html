    class main_queue

    source

    main_queue - things to run on the MAIN thread, handed over from other threads. What on_main { } puts its block into.

    launch_on(dispatchers.io(), { ->
    found := load_from_disk();          // slow: on a background thread
    on_main {
        tasks.replace_all(found);       // the screen's data: on the main thread
    };
});

    WHY THERE IS A MAIN THREAD AT ALL. The screen is built, laid out and painted by one thread - the one that called gui.run. If another thread changed a state in the middle of that, the screen could be built from data that is half old and half new, or a list could change under the loop that is walking it. So the rule (the same in Android, iOS, Swing, Qt): slow work goes to a background thread; everything the screen reads is changed only on the main thread. on_main is the door back.

    THE RULE IS CHECKED: changing a state from a background thread while a window is open stops the program with a message that says to use on_main (state.sharp) - it does not corrupt the screen at random some time later.

    The window's loop runs what is waiting once every turn, in the order it was handed over, and is woken at once when something arrives.

    WITHOUT A WINDOW (a console program, a test of a view model) nothing takes the blocks out by itself: call main_queue.run_waiting() where you want them run - a test does that right after the work it started has finished. (Android: Handler(Looper.getMainLooper()).post / Dispatchers.Main. Swing: SwingUtilities.invokeLater.)

    class timer

    source

    timer - run something later, or again and again.

    gui.after(2) { banner.value = 0; };              // once, two seconds from now
    tick := gui.every(1) { seconds.value += 1; };    // every second
...
tick.cancel();                                   // stop it

    The function runs on the same thread as everything else in the UI, between frames - so it may change state freely, and the screen follows. A timer costs nothing while it waits: an idle app sleeps until the next one is due. (Android: Handler.postDelayed. JavaScript: setTimeout / setInterval.)

    Timers belong to the PROGRAM, not to a widget: one made by a composable keeps running after that composable has left the screen, until it is cancelled. Make them where things happen once (main, a click handler) - not as a field of a composable, which is made anew on every rebuild of its parent.

    HOW IT WORKS: every live timer is in one list (all). Once per turn of the host's loop, run_due() calls those whose time has come; a repeating one is given its next time, a one-shot is dropped. When the host is about to sleep it asks next_due_in() how long until the soonest timer, and sleeps no longer than that (host.sharp, "rest").

    A timer may be made before the window exists (before gui.run): it has no clock to read yet, so it only remembers its delay, and its first due time is worked out on the first turn of the loop.

    class ui_host

    source

    ui_host - runs an app: owns the window and the tree, and turns the crank.

    gui.run(...) makes one and calls run(). There is one live host at a time (ui_host.current); widgets reach it for the theme, fonts, the focus and to ask for another frame.

    THE LOOP - every turn:

    1. EVENTS    read what happened and route it: the mouse to the view
             under it, keys to the focused view (input, below)
2. REBUILD   every composable whose state changed runs build() again
             and its new widgets are settled in (reconciler.sharp)
3. LAYOUT    if anything changed size: measure, then arrange, the tree
4. PAINT     if anything changed: paint the tree and show the frame
5. REST      nothing changed and nothing is animating: SLEEP until the
             next event instead of spinning

    Step 5 is why an idle Sharp app uses no processor and does not drain a battery: a screen that is not changing is not repainted. A widget that animates asks for the next frame with request_frame(); a widget that needs a repaint later (a blinking text cursor) with wake_in(seconds). (A game's canvas simply asks for a frame every frame.)

    THE FRAME RATE (gui.frame_rate, 60 unless the program says otherwise)

    Step 4 paints at most that many times a second. While something moves, the loop SLEEPS between two frames instead of painting the next one at once - so 30 does about half the work of 60, and 10 is visibly jerky and costs very little. Events are still read the moment they arrive; only what they change on the screen waits for the next frame. With 0 there is no limit at all: frames are painted and shown as fast as the machine can.

    The loop times the frames itself for every limit, and showing a frame never waits for the screen's refresh (follow_frame_limit says why).

    INPUT ROUTING

    mouse The view under the mouse is found from the tree (view.find_at); the nearest INTERACTIVE view at or above it becomes hover. On a press that view becomes active and keeps getting the mouse until the release, also when the mouse leaves it (dragging). A release still over it is a click. wheel Goes to the nearest view at or above the mouse that scrolls. keys Go to the view with the FOCUS (clicking a focusable view gives it the focus; Tab and Shift+Tab move it). Enter or Space on a focused clickable view clicks it.

    hover / active / focus are pointers INTO THE TREE. When a rebuild replaces the views they point at, the reconciler tells the host (replace_view) and the pointers move to the new views - so focus survives a rebuild.
