    class animated

    : state_cell · source

    animated - a number that GLIDES to a new value instead of jumping there.

    class drawer base composable {
    width := animated(0);                       // starts at 0, not moving
    override def build() : element {
    return row(modifier().fill()) {
        column(modifier().width(width.value).fill_height()) { ... }
        button("Menu") { toggle(); };
    };
}
        def toggle() {
        if(width.target() == 0) { width.go(240, 0.25); }    // glide to 240 over a quarter second
        else { width.go(0, 0.25); }
    }
}

    Read .value wherever a number is wanted - a size, a position, an opacity, a colour channel - and call .go(to, seconds) to send it somewhere. While it moves, whatever was built from it is rebuilt every frame; when it arrives the rebuilding stops.

    .value where it is now .go(to, seconds) glide there (from wherever it is, also mid-flight) .jump(to) be there at once .target() where it is heading (or resting) .moving() 1 while it is on its way

    The movement eases out: quick at first, settling gently - how things that come to rest look. (Compose: Animatable / animateFloatAsState. Android: ValueAnimator. CSS: a transition.)

    HOW IT WORKS

    Inside, the current value is an ordinary state<decimal> (shown) - so "who rebuilds when it changes" is the same machinery as for any state: the composables whose build() read it.

    An animated that is on its way is in one list (running). Once per turn of the host's loop, step_all() works out where each of them is for the current time and writes that into its state, which rebuilds its readers. While the list is not empty the host keeps producing frames.

    Made with a composable's own animated(...), it is remembered like a state: when a parent rebuilds and makes the composable again, the new animated takes over where the old one was - mid-flight included.

    class fader

    base widget : behavior, stateful · source

    fader - content that fades in when it should be seen and fades out when it should not. Made with fade(...).

    saved := state(0);
    fade(saved.value) {                         // there while saved.value is not 0
    text("Saved!").color(t.success);
}
    fade(show_help.value, modifier().fill_width()) { help_panel(); }.time(0.4)

    When the number turns from 0 to something else the content fades in; when it turns back to 0 it fades out, and once it has faded out it takes no room at all (the things around it close up).

    .time(seconds) how long a fade takes (default 0.18) .keep_room() stay the same size while invisible, so nothing around it moves

    (Compose: AnimatedVisibility with fadeIn / fadeOut. Android: a ViewPropertyAnimator on alpha. CSS: a transition on opacity.)

    HOW IT WORKS

    amount is how visible the content is right now, 0 .. 1. Every frame it is painted, it moves toward where it should be (1 when wanted, 0 when not) by the time that passed, sets its view's opacity to that, and asks for another frame until it has arrived. Then it stops asking, and an idle app goes back to sleep.

    The decision to fade is made by YOUR state turning; but a state change rebuilds the screen and makes a NEW fader. So the fader is stateful: the new one adopts the old one's amount, finds it is not where it should be, and that difference is the animation. A fader that is new on the screen (nothing to adopt) starts where it should be, without animating.

    The content is built even while it is invisible - it has to exist to fade out, and building it is cheap. What is skipped while fully faded out is measuring, placing and painting it.

    class glide

    source

    glide - boxes that move to their new place instead of jumping there. FRAMEWORK USE: apps ask for it with .animate_items() on a column or row and modifier().animate_size(); the host calls the functions here.

    THE IDEA (known as FLIP: first, last, invert, play)

    When a list changes - a row is added, removed, moved - layout simply puts every row where it now belongs. Nothing about layout is animated. Instead:

    1. each box remembers where the LAST layout put it (view.was_x / was_y,
   relative to its parent, so scrolling the parent is not a "move");
2. after the new layout, a box that is somewhere else gets a SHIFT that
   paints it exactly where it was a moment ago;
3. the shift is then run down to 0 over a quarter of a second.

    To the eye the row slides from its old place to its new one. To layout, and to the mouse, it has been at the new place all along.

    A box with no past in a container that has one is NEW: it fades in and drops a few pixels into place. A row that is removed is simply gone - and the rows below glide up into the room it left.

    WHICH BOX IS "THE SAME BOX" after a rebuild is the reconciler's business (reconciler.sharp): it matches by key first, then by position, and carries the memory over. So give rows a key - modifier().key(task.id) - or the row at position 3 is "the same" as whatever was at position 3 before, and nothing appears to move.

    (Compose: Modifier.animateItem() in lazy lists, animateContentSize(). Android: RecyclerView's DefaultItemAnimator, LayoutTransition.)

    class revealer

    base widget : behavior, clipper, stateful · source

    revealer - content that appears and disappears with a movement instead of popping. Made with animated_show(...).

    expanded := state(0);
    button("Details") { expanded.value = 1 - expanded.value; };
animated_show(expanded.value) {
    text("The long explanation ...");
};

    While visible is not 0 the content is there; when it turns 0 the content shrinks away (and what was below it moves up as it does), and comes back the same way.

    The plain way - if(expanded.value == 1) { text(...); } - still works and is right for most things; it just pops. (Compose: AnimatedVisibility with expandVertically + fadeIn.)

    HOW IT WORKS: progress runs between 0 (gone) and 1 (fully there) towards what is wanted. The widget is as tall as its content times the progress, cuts the content off at its own edge, and paints it as solid as the progress. While the progress is on its way, the tree is laid out again every frame. The widget is stateful: a rebuild in the middle carries the progress on. The very first time it is simply open or closed - nothing animates when a screen first appears.

    The content is built even while it is hidden (it must still be there to shrink away). Keep heavy things out of it, or behind an if of their own.

    class stagger

    source

    stagger - the "loose" scrolling feel: while a list is moving, each row lags a little behind the one before it, so the rows spread apart; as the movement dies down they close up again.

    scroll { column { ... } }.scroll_feel(SCROLL_STAGGER);
lazy_column { ... }.scroll_feel(SCROLL_STAGGER);

    FRAMEWORK USE: a scroller or lazy list owns one of these and feeds it.

    HOW IT WORKS

    speed is how fast the content has been moving lately: every scroll adds the distance it moved, and every frame a share of it drains away, so it rises while you scroll and falls back to 0 after.

    A row's lag is the speed times how far the row is from the LEADING edge: content moving up leads with its top, so the rows near the bottom lag most; moving down it is the other way round. The lag is only painted (view.sway_y) - layout never hears of it, so nothing can end up in the wrong place when the movement stops.

    (iOS Messages has this feel; Android's RecyclerView can be given it with an item animator and a scroll listener. Compose: per-item graphicsLayer translation driven by scroll velocity.)
