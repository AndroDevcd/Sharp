    class composable

    : element, behavior, stateful · source

    composable - a piece of screen you write yourself: some state, and a build() that turns that state into widgets.

    class counter base composable {
    count := state(0);
        override def build() : element {
        return gui.column().gap(12).center()
            .add(gui.text("count: " + count.value).size(28))
            .add(gui.row().gap(8)
                .add(gui.button("-", { -> count.value -= 1; }))
                .add(gui.button("+", { -> count.value += 1; })));
    }
}
    gui.run("Counter", 360, 240, new counter());

    build() describes what the screen looks like RIGHT NOW. It is called again whenever one of this composable's states changes - you never update the screen by hand. Keep build() free of side effects: it only reads state and returns widgets; things happen in the click handlers.

    A composable is itself an element, so composables nest like any widget:

    gui.column().add(new counter()).add(new counter())      // two independent counters

    PASSING THINGS IN: give your composable a constructor and keep what it was given in fields; build() reads them. (Compose calls these parameters, React "props".)

    (The name is composable because component is a word the Sharp language keeps for itself.)

    HOW IT WORKS INSIDE

    A composable has its own view in the tree with exactly one child: whatever build() returned. For layout and painting it is invisible - it measures as its child and places its child over itself.

    When a state that this composable's build() read changes, the state calls invalidate(), which puts the composable on the host's list; before the next frame the host calls rebuild(): build() runs again, and the reconciler settles the new widgets in, carrying over what the old ones remembered (reconciler.sharp). While build() runs, the host's building points at this composable - that is how a state knows who is reading it (state.sharp).

    When a PARENT rebuilds, its build() makes this composable again - a NEW object with states at their starting values. The reconciler pairs the new object with the old one and the new one adopts the old states' values (adopt, below). From then on the old object forwards to the new one (replaced_by), in case a click handler still holds it.

    class reconciler

    source

    reconciler - settles freshly built widgets into the tree, carrying over what the widgets they replace had remembered.

    THE PROBLEM: build() makes NEW widget objects every time. If the screen simply swapped to the new tree, everything that lives in the widgets and not in your state would reset on every change: the list would jump back to the top, the text cursor would vanish, the focused field would lose focus, a nested counter would forget its count.

    THE ANSWER: walk the old tree and the new tree side by side. Where a new widget sits in the place of an old widget OF THE SAME KIND, the new one takes over the old one's memory:

    old tree                 new tree
column                   column            same kind  -> carry over
  text "count: 1"          text "count: 2"   same kind  -> carry over (nothing to carry)
  scroller (at 240px)      scroller          same kind  -> scroll position carried
    ...                      ...
  button                   checkbox          different  -> the checkbox starts fresh

    "The same place" is the same position among the siblings - or, for widgets that were given a key (modifier().key("row-17")), the sibling with the same key, so a reordered list keeps each row's memory with the row.

    What "memory" is, is up to each widget: it implements stateful and copies what it wants in adopt(old). The reconciler itself carries the things every view has: is the mouse over it, is it pressed, does it have the focus.

    Composables are where it recurses in an interesting way: a new composable first adopts the old one's STATES (so its build() sees the remembered values), then builds, then its result is settled against the old result.

    (React calls this "reconciliation"; Compose does the equivalent with its slot table. This one is deliberately the simple version: the NEW tree always becomes the live tree, and only memory moves across.)

    Functions

    static def retire(old: view)

    old is a subtree that is not on the screen any more. Every composable in it whose place was NOT taken by a new object is gone for good: it is told (composable.left), and so is everything it had built.

    A composable that WAS replaced carries on in its new object; what it had built was handed to the new object's rebuild, which retires the leftovers of that itself - so the walk stops there.

    static def settle(fresh: view, before: view?)

    Make fresh (a subtree that was just built) ready to live in the tree. before is the subtree it replaces, or null when nothing was there.

    class state<t>

    : state_cell · source

    state<t> - a value the screen depends on.

    count := state(0);                       // inside a composable
    gui.text("count: " + count.value)        // read it while building the screen
count.value = count.value + 1;           // change it: the screen rebuilds by itself
count.value += 1;                        // the same

    That is the whole idea of a declarative UI: you never reach into the screen to change a label. You change the STATE, and the part of the screen that was built from it is built again.

    value is a property (a field with a getter and a setter): reading it hands back what is held; writing it stores the new value and tells the screen. Compose comparison: mutableStateOf(0) and its .value. React: useState.

    WHO REBUILDS: exactly the composables that READ the state while building.

    The getter looks at which composable's build() is running right now (ui_host.building) and writes it down as a reader. The setter tells every reader to build again, and forgets them - they sign up again when their build() reads the state anew.

    So it does not matter where a state was made. A state made at the top of the app and read only by one small composable deep inside rebuilds only that one. A state nobody reads while building rebuilds nothing. (Compose does this with its "snapshot" read tracking - Composition.recordReadOf; this is the same idea in its simplest form.)

    THREE THINGS TO KNOW (they come from how Sharp treats values): - A yes/no state is a number: state(0) / state(1), tested with flag.value == 1. (A bool variable is a shared object in Sharp; numbers are plain values.) - A text state hands you ITS string. Build a new text and assign it (name.value = name.value + "!"); do not change the string you were handed in place, or the screen will not know. - Changing something INSIDE an object held by a state (a field of it, an item of a list) does not go through the setter. Call touch() afterwards.

    interface state_cell

    source

    What a composable knows about each of its states without knowing the type inside: that it can take over the value of the state it replaces.

    WHY THIS EXISTS: when a screen is rebuilt, a parent's build() makes its child composables AGAIN - new objects, with new states at their starting values. The reconciler pairs each new composable with the old one it replaces and has every new state take the old state's value, in the order they were made. So the counter keeps counting although its object is new. (React keeps hook state by call order in the same way; Compose keeps remembered values by position in its slot table.)

    class state_list<t>

    source

    state_list - a list the screen watches: add, remove or move an item and every screen that showed the list is built again.

    tasks := state_list<task>();
    tasks.add(task("Write the notes"));         // the screen follows
tasks.remove(done_one);
tasks.move(0, 3);
    for(i : _int64 = 0; i < tasks.size(); i++) { task_row(tasks.at(i)); }

    WHY NOT state<list<t>>: a state only notices that it was given a NEW value. Adding to the list it already holds changes nothing it can see, so the screen would stay as it was (unless you remember to call touch()). This class does the remembering: every function that changes the list announces it.

    Changing something INSIDE an item (task.done = 1) is still invisible to the list - it holds the same item as before. Say so with changed():

    t.done = 1;
tasks.changed();

    (Compose: mutableStateListOf / SnapshotStateList.)
