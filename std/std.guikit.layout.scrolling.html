    std.guikit.layout.scrolling module

    lazy_list scroller

    class lazy_list

    base widget : behavior, clipper, wheel_target, drag_scroller, stateful, overlay_painter · source

    lazy_list - a scrolling list that only builds the rows you can see. Made with lazy_column(...).

    lazy_column(modifier().fill()) {
    item { text("Contacts").size(22).bold(); }          // one fixed row
    items(people.size()) { i: _int64 ->           // one row per person,
        contact_row(people.at(i));                      // built only when it scrolls into view
    }
    item { text("end of list").dim(); }
}.gap(4)

    A plain scroll { } builds, measures and keeps EVERY child, visible or not: fine for dozens of rows, hopeless for fifty thousand. A lazy list is told HOW MANY rows there are and HOW to build row i, and it builds just the handful that fit the window - so a list of a million rows opens instantly and scrolls smoothly.

    .gap(n) room between the rows

    ONLY item { } AND items(n) { i -> } GO INSIDE lazy_column { }. A widget written straight into the block would be built eagerly, which is exactly what this list exists to avoid - so that is an error, and so is item or items anywhere else (scope.inside).

    (Android: RecyclerView with an adapter. Compose: LazyColumn with item / items. The idea is the same in all of them: "virtualisation".)

    HOW IT WORKS

    The scroll position is not a number of pixels (nobody knows how tall a million rows are without building them). It is "which row is at the top, and how many pixels of that row have scrolled out": first and first_cut. (Compose's LazyListState keeps the same pair: firstVisibleItemIndex and firstVisibleItemScrollOffset.)

    Every layout, fill works from that pair: 1. if the top row has scrolled DOWN past the top edge (first_cut below 0), build the rows before it until the gap is covered; 2. if the top row has scrolled entirely out, let it go and move on to the next; 3. from the top row, build and measure row after row until the window is full; 4. if the rows ran out before the window was full, the list was scrolled past its end: pull it back and go again.

    The rows that exist right now are the list's children (rows, with rows_first the number of the first of them) - so painting, clicking and focus work on them like on any other widgets. Rows that leave the window are dropped; rows that come in are built by the section's function.

    WHO REBUILDS: a row is built during layout, not during anyone's build(). So the list remembers the composable that was building when the list itself was made (owner) and puts it back as "the one building" while a row's function runs. A state read inside a row therefore signs up that composable; when the state changes, it rebuilds, makes a new lazy list, and the visible rows are built afresh from the new data.

    ACROSS A REBUILD the new list adopts the scroll position, and each row it builds takes over the memory of the old list's row with the same number (the reconciler) - so a counter or a text field inside a visible row keeps what it had. A row that scrolls out of view is gone, and with it what only that row remembered; keep what matters in your own state.

    The scroll bar is an estimate: rows are assumed to be as tall, on average, as the ones built so far.

    class scroller

    base widget : behavior, clipper, wheel_target, pointer_target, drag_scroller, stateful, overlay_painter · source

    scroller - a window onto content that is bigger than the room there is.

    scroll(modifier().fill()) {                       // scrolls up and down
    for(i : _int64 = 1; i <= 200; i++) { text("row " + i); }
}
    scroll_row(modifier().fill_width()) {             // scrolls sideways
    for(i : _int64 = 0; i < count; i++) { photo_card(i); }
}

    The content is laid out at its full size along the scrolling direction; the scroller shows the part that fits and lets the wheel (or dragging the bar) move it. Give the scroller a limit that way - modifier().fill(), .grow(1), .height(n) - otherwise it is simply as big as its content and there is nothing to scroll.

    A sideways scroller moves with the wheel too (and with a sideways wheel or touchpad swipe). When a scroller is already at its end, the turn of the wheel is passed on to a scroller around it.

    HOW IT WORKS: the scroll position is offset, the number of pixels the content has moved (up, or left). arrange() places the content that far before the scroller's own corner, and the scroller is a clipper, so the view paints the content cut off at the scroller's edges and the mouse cannot reach things that are scrolled out. Scrolling changes offset and arranges again - it does not rebuild anything.

    The offset is the scroller's own memory (not your state), so it implements stateful: when the screen is rebuilt, the new scroller adopts the old one's offset and the list stays where the user left it.

    Both directions are ONE class: sideways says which way is "along". The few places that differ ask long_of_me() instead of naming width or height. (Compose: Modifier.verticalScroll / horizontalScroll. Android: ScrollView / HorizontalScrollView.)
