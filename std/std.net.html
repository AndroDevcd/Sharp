    interface connection

    source

    A CONNECTION: one end of a conversation in bytes, whatever carries it

    tcp_socket (plain) and tls_socket (encrypted) are both one, so code written against connection - the HTTP client, a line protocol of your own - works over either:

    def greet(line: connection) {
    line.write(hello, sizeof(hello));
    answer := line.read(4096);
}

    The three things every connection does:

    read(most)          wait for bytes and return them: at least one, at most `most`.
                    An EMPTY array: the other side has closed and all it sent was read.
write(data, count)  send the first `count` bytes of `data`, all of them
close()             close this end; twice does nothing
    Java comparison: the InputStream and OutputStream of a java.net.Socket.

    class datagram

    source

    NETWORKING WITHOUT CONNECTIONS (UDP), and looking up names (DNS)

    // one side
ear := udp_socket.bind(9000);                   // listen on port 9000
got := ear.receive();                           // waits for a datagram
print(got.text() + " from " + got.host + ":" + got.port + "\n");
ear.send_text(got.host, got.port, "pong");      // answer where it came from
    // the other
mouth := udp_socket.open();                     // any free port
mouth.send_text("192.168.1.20", 9000, "ping");
answer := mouth.set_timeout(1000).receive();

    TCP is a connection: everything arrives, in order, or the connection breaks. UDP sends single DATAGRAMS - a block of bytes to an address - with no connection and no promise: one may be lost, come twice, or come out of order, and nobody says so. In return there is no setup and no waiting, which is what games, voice, sensors and "who is on this network?" broadcasts want. A datagram arrives whole or not at all; keep them under about 1200 bytes and they travel in one piece.

    udp_socket.open()                   a socket on any free port
udp_socket.bind(port)               ... on that port, reachable from other machines
udp_socket.bind(port, true)         ... from this machine only
send(host, port, bytes)   send_text(host, port, text)
receive()                           the next datagram (waits; socket_timeout after set_timeout's time)
allow_broadcast()                   may send to "255.255.255.255": everyone on the local network
port()   close()
    dns.lookup("example.com")           every address (version 4) the name has, as texts
dns.first("example.com")            the first of them
    Java comparison: DatagramSocket / DatagramPacket, InetAddress.getAllByName.

    class http

    HTTP IN ONE LINE

    page := http.GET("https://example.com/").text();
    answer := http.POST("https://httpbin.org/post") {
    it.header("X-Trace", "abc");
    it.json("hello", "world");
};

    class http_client

    : http_engine · source

    THE HTTP CLIENT: sends requests over the network (HTTP/1.1, http and https)

    Most programs never make one: http.GET(...) and every http_service use a shared one. Make your own to give it other settings:

    client := new http_client();
client.wait = 5000;                 // milliseconds of silence before a request gives up (30000)
client.most_redirects = 3;          // "go there instead" answers followed per request (10)
client.agent = "my-app/1.0";        // the User-Agent header
answer := client.send(new http_request("GET", "https://example.com/"));

    WHAT IT DOES FOR YOU - https: the connection is a tls_socket, so the server's certificate is checked (tls.sharp); - connections are KEPT and used again: the second request to a server does not connect (or do the TLS handshake) again. A kept connection the server has closed meanwhile is noticed and the request sent anew; - redirects are followed (301, 302, 303, 307, 308), the way a browser does: 303 - and a POST that gets 301 or 302 - goes on as a GET, 307 and 308 repeat the request as it was. Authorization is not carried to another server; - bodies in pieces ("chunked") are put together; - it tells servers it reads compressed answers (gzip) and unpacks them: text and json usually travel at a fifth of their size.

    WHAT IT THROWS: http_exception when there is no answer (http_timeout when the server was silent too long). An answer is returned whatever its status - 404 and 500 are answers; require_ok() turns them into http_status_exception.

    One client can be used by several threads at once: each request has a connection to itself.

    Not done: HTTP/2, proxies, cookies kept between requests.

    class http_error

    base exception · source

    AN HTTP SERVER: routes, written the way the client's are

    class user { id : _int64 = 0; name : string = ""; }
class new_user { name : string = ""; }
    server := new http_server();
    server.GET("/hello") { it.text("hello"); };
    server.GET("/users/{id}") {
    found := users.find(it.number("id"));
    if(found == null) { throw new http_error(404, "no such user"); }
    it.json(found!!);                               // an object of yours, as json
};
    server.POST("/users") {
    wanted := it.body<new_user>();                  // the json body, as an object of yours
    it.status(201).json(users.add(wanted.name));
};
    server.files("/static", "public");                  // GET /static/app.js  ->  the file public/app.js
server.socket("/live") { ... };                     // a websocket (`it` is a web_socket)
server.serve(8080);                                 // runs until stop()

    A ROUTE is a method and a path; a part in braces takes whatever stands there ("/users/{id}" answers /users/7 and /users/ann). The block runs for each request with it, an http_exchange: the request to read and the answer to give.

    READ THE REQUEST GIVE THE ANSWER it.method() it.path() it.text("...") plain text it.path("id") a part in braces it.html("...") it.number("id") ... as a number it.json(object) an object, a list, a json_value it.query("q") ?q=... (null: none) it.bytes(data, type) it.header("x") (null: none) it.file(new file(...)) it.body_text() it.body_bytes() it.redirect("/login") it.body_json() a json_value it.status(201) (before the body; 200 without it) it.body<t>() an object of t it.header("X-Name", "value") it.remote() who is asking (nothing at all answers 204, "done, no content")

    WHEN A HANDLER THROWS: http_error(status, message) is answered with that status and {"error": message}; anything else is a 500, printed with where it happened. No route for the path: 404; a route, but not for that method: 405.

    server.before { ... }       runs before every handler; when it answers (say 401) the handler is skipped
server.after { ... }        runs after it, the answer still open to change (a header for all)
server.start(8080)          serve in the background and return the port (0: any free port)
server.start(8080, true)    ... for this machine only (127.0.0.1)
server.serve(8080)          serve and wait
server.stop()
server.workers = 32;        requests served at the same time (16)

    Each request runs on one of the server's threads, several at once: what handlers share has to be guarded (lock, an atomic, a database).

    This is plain HTTP/1.1. For https put a reverse proxy in front (Caddy, nginx), which is how servers are run anyway.

    Java comparison: Javalin / Spark - app.get("/users/{id}", ctx -> ...);
Python: Flask's @app.get("/users/<id>"); JavaScript: Express.

    class http_request

    source

    ONE REQUEST, being put together

    asked := new http_request("POST", "https://api.shop.example/v2/products/{id}/photo");
asked.path("id", 7)                     // fills {id} in the address
     .query("size", "large")            // ...?size=large
     .header("Accept", "application/json")
     .bearer(token)                     // Authorization: Bearer ...
     .json("caption", "front view");    // the body: {"caption":"front view"}

    Every word returns the request, so they chain; in the block of http.POST(...) { } the request is it, and in an http_service the same words are written bare.

    OTHER timeout(milliseconds) give up when the server is silent for this long follow_redirects(false) hand back a "go there instead" answer as it is

    Each function of the service is one line: the VERB is the function called (GET, POST, PUT, PATCH, DELETE - in capitals, as HTTP writes them), the type in <...> is what the json answer is turned into (json.sharp: any class of yours, list<t>, a generic class like page<product>), and the block says what goes into the request.     IN THE BLOCK (each is explained in http_request.sharp) path(name, value) fills {name} of the route query(name, value) ?name=value (a null value leaves it out) header(name, value) bearer(token) basic(user, password) accept(type) send(object) the body: an object of yours, as json json(name, value) the body: a json object, member by member form(name, value) the body: a form part(name, value) part(name, file, type) the body: a form in parts, with files body(text) body(text, type) body(bytes, type) body(json_value) timeout(milliseconds)

    IN THE CONSTRUCTOR - for every request of the service base_url(address) what every route is appended to header(...) bearer(...) basic(...) accept(...) timeout(...) the same words: outside a block they are for all requests retry(times, wait) try again (after wait ms, then twice that ...) when there is no answer or the server says 502, 503 or 504 - only for requests that are safe to repeat (GET, HEAD, PUT, DELETE) before { ... } runs on every request before it is sent (it is the request): add a token after { ... } runs on every answer (it is the response): notice a 401 log(http_log.basic) print each request and answer: basic (one line each), headers, body use(engine) send through another engine: a client with other settings, a fake_http in a test

    class socket_exception

    base io_exception · source

    NETWORKING: connections between programs (TCP)

    // a client
connection := tcp_socket.connect("example.com", 80);
connection.write_text("GET / HTTP/1.0\r\nHost: example.com\r\n\r\n");

    guest := server.accept();                   // waits for someone to connect

    guest.close();
}

    A tcp_socket is one end of a connection: what is written at one end is read at the other, in order, nothing lost. A tcp_server waits on a port for others to connect and hands out a tcp_socket for each.

    WAITING. connect, accept, read and write wait until they are done - a read until at least one byte has arrived or the other side has closed. Other threads go on meanwhile, so a server usually gives each guest a thread of its own. set_timeout(ms) makes read and write give up after that long (socket_timeout).

    WHEN SOMETHING GOES WRONG - nobody listens there, the name is unknown, the connection broke - a socket_exception says what the system said.

    Addresses are internet version 4 ("93.184.216.34", or a name that has such an address); nothing is encrypted.

    All of it is Sharp: the system's socket functions are called directly (system_sockets.sharp).

    Java comparison: java.net.Socket and ServerSocket; Python: socket.

    class web_socket_exception

    base socket_exception · source

    WEBSOCKETS: a connection both sides can send on at any time, in whole messages

    chat := web_socket.connect("wss://chat.example/room/7");
chat.send("hello");                         // a text message
while(true) {
    message := chat.receive();              // waits for the next one; null: the other side closed
    if(message == null) { break; }
    print(message!!.text() + "\n");
}
chat.close();

    HTTP answers once per request. A websocket starts as an HTTP request ("may we switch?") and from then on is a two-way pipe of MESSAGES: what one side sends as one message arrives as one message, however large, text or bytes. It is what chats, live dashboards and games use.

    web_socket.connect(address)             "ws://..." (plain) or "wss://..." (encrypted, the server's certificate checked)
web_socket.connect(address) { ... }     with a block for the opening request (`it` is an http_request: headers, a token)
send(text)   send_bytes(data)           one message
receive()                               the next message (web_message), null when the other side has closed
receive_text()                          the next message as text, null when closed
ping()                                  "are you there?" - answered by the other side without the program seeing it
set_timeout(ms)                         receive() gives up after this long (socket_timeout); 0: waits for ever
close()   close(code, reason)           say goodbye and close (1000 is "done")

    A server takes websockets on a route of an http_server: server.socket("/room/{id}") { ... } (http_server.sharp).

    Pings from the other side are answered by receive(), so a program that wants to stay connected keeps calling it. One thread may receive while another sends.

    Java comparison: java.net.http.WebSocket; JavaScript: new WebSocket(url).
