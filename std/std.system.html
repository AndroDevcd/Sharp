    class args_exception

    base exception · source

    Thrown by args_parser.parse() when the command line does not fit what the program declared: an unknown option, an option without its value, a missing required option or argument, too many arguments, a value that is not a number where one is needed.

    The message is meant for the user of the program, e.g.

    unknown option --colour
option --output needs a value
missing required argument <source>

    The usual reaction is to print it together with parser.usage() and exit with a code other than 0.

    class args_option

    source

    One thing an args_parser knows about: a flag (--verbose), an option with a value (--output FILE) or a positional argument (<source>), with its description and - after parsing - what the command line gave for it.

    Programs declare these through args_parser.add_flag / add_option / add_positional and read the results through the parser; this class only holds the data.

    class args_parser

    source

    Takes the command line of a program apart: flags, options with values and positional arguments, with defaults, checks, and a generated help text.

    def main(args: string[]) {
    parser := new args_parser("copytool", "Copies files with style.");
    parser.add_flag("verbose", 'v', "print what is being done");
    parser.add_option("jobs", 'j', "N", "how many copies run at once", "4");
    parser.add_required_option("output", 'o', "DIR", "where the copies go");
    parser.add_positional("source", "the file to copy", true);
    try {
    parser.parse(args);
} catch(e: args_exception) {
    println(e.get_message());
    println(parser.usage());
    exit(2);
}
if(parser.help_requested()) { println(parser.help()); exit(0); }
        jobs := parser.number("jobs");          // 4 unless -j / --jobs was given
    if(parser.flag("verbose")) { ... }
    source := parser.value("source");
}

    What a command line may look like: --name a flag -n its one-letter form --name value an option -n value its one-letter form --name=value the same -nvalue the same -abc several one-letter flags at once (the last may be an option that takes the next argument as its value) -- everything after it is a positional argument, even when it starts with a dash - a single dash is a positional argument (by custom: "standard input") anything else a positional argument

    An option takes the next argument as its value whatever it looks like, so "--count -5" works. An option or flag may appear several times: value() gives the last one, values() all of them, count() how many.

    --help and -h are understood without being declared (unless the program declares "help" or 'h' itself): they set help_requested(), and then the checks for required options and arguments are skipped.

    Everything that does not fit throws args_exception (see there). Declaring something twice, or asking for a name that was never declared, is a mistake in the program and throws illegal_argument_exception.

    A parser can parse several times; each parse starts fresh. Not thread safe.

    Take the command line args apart (the arguments as main() gets them, without the program name). Throws args_exception when it does not fit the declarations.

    def whole_number(name: string) : decimal

    The value of name as a whole number. Throws args_exception when the value is not a whole number and illegal_argument_exception when name was never declared.

    class gc

    source

    THE GARBAGE COLLECTOR: when it runs, and what it has been doing

    A collection stops the program for a moment. Most programs never notice. One that draws a picture sixty times a second does: a pause in the middle of a frame is a frame that comes late. Such a program takes the decision for itself:

    gc.set_mode(gc_mode.manual);        // from here on nothing is collected ...
while(playing) {
    draw_a_frame();
}
gc.collect();                       // ... until the program says so
gc.set_mode(gc_mode.normal);

    or for one piece of code only, with the mode put back afterwards whatever happens in it:

    gc.during(gc_mode.manual) {
    play_the_level();
};

    MANUAL MEANS MANUAL. Nothing is freed until the program collects. If it never does, memory fills up to the limit (sharp -mem, a quarter of the machine's memory when not given) and the next new is out of memory. There is no rescue collection. So a program in manual mode watches what it uses and collects where a pause costs nothing:

    if(gc.pressure() > 0.8) { gc.collect(); }           // between two levels
if(gc.allocated_since_collection() > 4 * 1024 * 1024) { gc.collect_young(); }

    OUT OF MEMORY, in either mode, is not the end at once. Past the limit lies a small reserve (a 32nd of the limit, 4 MB at most) that ordinary code can never use; it is there so that what answers an out of memory has room to work in. Three things happen, in this order:

    1. THE HOOK, when the program has one:

    gc.on_out_of_memory({ ->
    textures.drop_unused();
    gc.collect();
});

    The thread that ran out waits; the hook runs on a thread of its own (memory watcher, like the hooks of signals), so it is ordinary code. When it has brought memory back under the limit the program goes on exactly where it was - nothing was thrown, nothing unwound. 2. ONE EXCEPTION, when there is no hook or it did not help: the next new throws an out_of_memory_exception, for a try/catch to take:

    try {
    level = load_level(name);
} catch(none_left: out_of_memory_exception) {
    cache.clear();
    gc.collect();
}

    3. THE END, when the reserve is used up as well: by a handler that needed more than the reserve, or by a program that caught the exception and went on without freeing anything. The VM prints what memory looked like and the program ends. There is no third chance, so an out of memory can never follow an out of memory without end.

    It is over as soon as a collection leaves memory under the limit: the reserve is whole again for the next time. gc.collect() and gc.collect_young() make no objects themselves and always work.

    A hook must not wait for a lock that a thread which ran out is holding: that thread waits for the hook. An exception a hook throws ends that hook, is printed, and the hooks after it still run.

    TWO KINDS OF COLLECTION gc.collect_young() looks at what was made since the last collection. Short: its cost follows what is new, not everything alive. gc.collect() looks at everything. It frees what a young one cannot (objects that lived long and then died), and takes longer the more is alive. Both work in either mode, and both are done when the call returns.

    THREADS. The mode belongs to the whole program, not to the thread that set it, and every function here may be called from any thread. When blocks of gc.during() run at the same time on several threads and ask for different modes, manual wins for as long as one manual block runs - it is the one that promised "no pause in here".

    C# comparison: GCSettings.LatencyMode and GC.TryStartNoGCRegion; Unity's
GarbageCollector.GCMode.Manual. Go: debug.SetGCPercent(-1). Lua:
collectgarbage("stop"). Go's collector still steps in at its memory
limit; here manual mode is out of memory instead. Java: an
OutOfMemoryError can be caught too, but with no reserve to handle it in.

    class logger

    source

    Writes log messages with a level, optionally a time stamp, and a name, to the console, to files, or to any text_writer.

    log := new logger("server");
log.add_console();
log.add_file(new file("server.log"));
log.set_level(logger.level_debug);
    log.info("listening on port 8080");
log.warn("disk almost full");
log.debug("request took 12 ms");
log.close();
    2026-11-12 09:30:00.123 INFO  [server] listening on port 8080

    Levels, from chatty to serious: trace, debug, info, warn, error. A logger writes the messages at its level and above (info by default) and drops the rest; logger.level_off silences it.

    Format. Every message becomes one line built from a pattern with the placeholders {time} {level} {name} {message}; the default is "{time} {level} [{name}] {message}". set_format() changes it. The level is padded to five characters so that the messages line up.

    Time. {time} is the time in UTC as "YYYY-MM-DD HH:MM:SS.mmm". The clock can be replaced with set_clock() (a function that returns milliseconds since 1970) - tests use that to get the same output on every run - or time stamps can be left out altogether with set_timestamps(false), which also removes "{time} " from the default format.

    Targets. A logger without a target writes nothing. File targets append to their file. By default every message is flushed to all targets right away, so nothing is lost when the program stops; for a file that means rewriting it on every message (the runtime cannot append), which is fine for ordinary logs and slow for very large ones - set_auto_flush(false) and flush() or close() at the end are the remedy.

    A file that must not grow without end: add_rotating_file("server.log", 1000000, 5) really appends (nothing is rewritten), and when the file passes a million bytes it becomes server.log.1 - the old .1 becomes .2, and so on, the fifth is deleted - and a new server.log is started.

    Several threads may log to one logger: each message is written whole, one after the other.

    class process

    source

    Runs a command of the operating system and tells what came out of it.

    result := process.run("git status --short");
if(result.succeeded()) {
    foreach(line in result.output_lines()) { println(line); }
} else {
    println("git failed (" + result.exit_code() + "): " + result.error_output());
}
    code := process.execute("make install");      // output goes straight to the console

    A process object is the finished result of one run: the command, its exit code, and everything it printed to standard output and to standard error.

    How it works: the runtime can hand a command line to the shell (sys()) but cannot talk to the running program. So run() sends the output of the command into temporary files, waits for the command to end, reads the files and deletes them. Consequences: output is available only when the command has finished (no live progress), and a command that waits for keyboard input should get its input from run_with_input().

    The command is a command line for the shell (/bin/sh on unix, cmd.exe on windows), so pipes, && and wild cards work - and anything put into it from outside has to be quoted: use process.quote() for every argument that is not a constant.

    Exit codes: 0 means success by convention. On unix a command that was ended by a signal reports 128 + the number of the signal, like the shell does, and "command not found" is 127.

    class signals

    source

    SIGNALS: being told when someone asks the program to stop, instead of being stopped

    signals.on_interrupt({ ->                   // Ctrl+C
    println("saving before I go...");
    save_everything();
    exit(0);
});
    signals.on_terminate({ -> server.stop(); });    // `kill`, the system shutting down
signals.on_hangup({ -> reload_settings(); });   // the terminal was closed (not on Windows)

    WITHOUT A HOOK each of the three ends the program at once, as always. WITH ONE the program is not ended: the hook runs, and what happens next is the hook's to decide - most end the program themselves with exit(), after putting things in order; a hook that returns lets the program run on.

    Several hooks for one signal run in the order they were added. signals.forget_hooks() takes them all away: the signals end the program again.

    WHERE A HOOK RUNS: on a thread of its own, started with the first hook (signal watcher, a daemon: it does not keep the program alive). NOT in the middle of whatever the program was doing when the key was pressed - that is what makes a hook safe to write: it is ordinary code, it may print, lock, allocate, wait. It is another thread, so what it shares with the rest of the program is shared as between any two threads (lock it). It runs within a few hundredths of a second of the signal.

    A PROGRAM THAT DOES NOT ANSWER CAN STILL BE STOPPED. If Ctrl+C is pressed three more times while a hook has not come back for the next one (it hangs, or it loops), the program is ended the plain way.

    WHAT CANNOT BE HOOKED: a crash. And under sdb, Ctrl+C belongs to the debugger: it pauses the program, and an interrupt hook is not run.

    An exception a hook throws ends that hook, is printed, and the hooks after it still run.

    C comparison: signal() / sigaction(), whose handler runs inside the
interrupted code and may call almost nothing. Go: signal.Notify, a
channel read by a goroutine - the same idea as here.

    Functions

    static def forget_hooks()

    take every hook away: Ctrl+C and the others end the program again

    static def on_hangup(hook: ()())

    run hook when the program's terminal is closed, instead of ending the program (never happens on Windows)

    static def on_interrupt(hook: ()())

    run hook when Ctrl+C is pressed, instead of ending the program

    static def on_terminate(hook: ()())

    run hook when the program is asked to end (kill, the system shutting down), instead of ending it

    class subprocess

    source

    A PROGRAM THIS PROGRAM STARTS AND TALKS TO WHILE IT RUNS

    child := subprocess.start("ping example.com");
while(true) {
    line := child.read_line();              // each line as the program prints it
    if(line == null) { break; }             // null: it has closed its output (it ended)
    println("> " + line!!);
}
code := child.wait();                       // its exit code
child.close();
    sorter := subprocess.start("sort");
sorter.write_text("pear\napple\n");
sorter.close_input();                       // "that was all": the program sees the end of its input
sorted := sorter.read_all_text();

    process.run() (process.sharp) runs a command to its end and then hands over everything it printed. A subprocess is for the rest: output read while the program still runs, input written to it as the conversation goes, a program that is stopped from here (kill), or one that is only asked now and then whether it is still running.

    ANOTHER SHARP PROGRAM is started with run(program, arguments), and any program by its file and arguments with start_program(file, arguments).

    THE COMMAND is a command line for the system's shell (/bin/sh on Linux, cmd.exe on Windows), as with process.run: pipes and && work, and anything put into it from outside is quoted with process.quote().

    THREE STREAMS connect the two programs: what is written here is the program's input; its output and its error output are read here, each on its own - or as one, in the order printed, with start(command, true). A read WAITS until something has arrived or the program has closed that stream. So a program that prints a lot on BOTH streams should be started merged, or have each stream read by a thread of its own: while this program waits on one, the other fills up and the program stops and waits for it to be read.

    close() lets go of the streams. It does not stop the program: kill() does.

    All of it is Sharp: posix_spawn and pipes on Linux, CreateProcess and pipes on Windows, called directly.

    Java comparison: ProcessBuilder and Process; Python: subprocess.Popen.

    Functions

    def close()

    Let go of the three streams (and, on Windows, of the system's handle of the program). The program is not stopped by this; one that still runs is not waited for either - wait() before close() when its exit code matters. Closing twice does nothing.

    def close_input()

    "that was all": the program reads the end of its input. Nothing can be written afterwards.
