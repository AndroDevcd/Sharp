    interface behavior

    source

    What every kind of widget must answer.

    The widget object holds its own view (me, from the widget base class), so these take no view argument.

    Functions

    def arrange()

    Your view now has its final place. Put your CHILDREN where they belong inside your content box (me.inner_x() ... me.inner_h()), each at the size its measure answered (kid.want_w x kid.want_h). Only positions are decided here; sizes were decided in measure. A widget without children does nothing here.

    def kind() : string

    A short name of the kind ("button", "column"). When the screen is rebuilt, a new widget only takes over the remembered state of an old one (scroll position, text cursor) when the kinds match.

    def measure(min_w: decimal, max_w: decimal, min_h: decimal, max_h: decimal)

    How big does your CONTENT want to be? It may be anything from min_w x min_h up to max_w x max_h (a max may be UNBOUNDED; min equal to max means the size is already decided). Answer by setting me.content_w and me.content_h; the view pulls the answer into the range, so a widget that just reports its natural size is correct.

    Padding and the size modifiers are the view's business, not yours: the numbers you get are already for the content alone.

    A container measures its CHILDREN here - every child exactly once, with the range it decides for that child - and answers from their sizes.

    def paint(p: painter)

    Paint your own content. The view has already painted the background and border; your children are painted after you return, on top.

    interface pointer_target

    source

    class scope

    source

    scope - what makes the nested, Compose-like way of writing a screen work:

    gui.column {
    gui.text("Hello");                       // lands in the column ...
    gui.row {
        gui.button("No") { answer(0); };     // ... these land in the row ...
        gui.button("Yes") { answer(1); };
    };
    if(show_hint.value == 1) {
        gui.text("ordinary `if` and `for` work in here").dim();
    }
}

    Nobody calls .add(). A widget made INSIDE a container's block becomes a child of that container, in the order the lines run.

    HOW: there is one "open container" at any moment (open, below).

    - A container given a block opens itself (remembering what was open before), runs the block, and puts the previous one back. Blocks nest, so this behaves like a stack - kept on the call stack by fill, with no list to manage. - Every widget, the moment it is made, asks the scope to adopt it (widget.attach, and the composable's constructor). If a container is open, the widget is added to it; if none is, nothing happens.

    That is all the "magic" there is. Compose does the equivalent in its compiler (every @Composable call gets a hidden composer argument that knows the current group); here it is one static field you can read.

    BOTH STYLES MIX. .add(child) still works everywhere, also inside a block: a widget that is already somewhere is MOVED, never duplicated (view.add_kid). So gui.row().add(gui.text("a")) written inside a column's block ends up as the column holding the row holding the text.

    Fields

    openview?the container whose block is running right now (null: none)

    Functions

    static def adopt(fresh: view)

    a widget was just made: if a block is running, it belongs to that block's container

    static def collect(as_kind: string, block: ()()) : view

    Run block on its own, into a container that is part of nothing, and hand that container back: its kids are the widgets the block made.

    For functions whose block does not describe CHILDREN but something else they want to look at first - the first screen of a screen stack, the options of a dropdown. as_kind is the kind the container reports while the block runs ("dropdown"), so that things which only belong in such a block (option(...)) can check they are in the right place (inside, below).

    static def fill(container: view, block: ()())

    run block with container as the open container, then put back whichever was open before

    static def inside(wanted_kind: string, written: string, belongs_in: string) : view

    SOME THINGS ONLY MAKE SENSE INSIDE ONE PARTICULAR PARENT: tab(...) inside tabs { }, item / items inside lazy_column { }, option(...) inside dropdown { }. Such a function calls this first. It hands back the open container when that is of the kind asked for - and otherwise stops the program with an error that says what was written and where it belongs:

    illegal_state_exception: `tab(...)` only works inside `tabs { ... }`
(here it was used inside a `column`)

    (Compose catches the same mistake at compile time with scope types - RowScope, LazyListScope. Sharp has no receiver types for blocks, so it is checked when the line runs: the first time the screen is built.)

    static def lone_row(space: decimal, block: ()()) : view

    Run block into a ROW of its own that belongs to nothing yet, and hand the row's box back: the widgets the block made sit in it side by side, space pixels apart.

    For a widget that takes a block for one PART of itself - the caption of a checkbox, the title of a tab: it makes the part with this, adds the box as its child and gives it a place in its own arrange().

    class view

    source

    view - one box on the screen, and one node of the tree.

    Every widget has exactly one view. The view holds what ALL boxes have in common and does the work that is the same for all of them:

    the tree         parent, kids
the box model    padding, fixed / minimum / maximum size, "fill", background,
                 corner radius, border
layout           measure() works out the size it wants, arrange() gives it
                 its final place - asking its behavior about the content
painting         background, border, then the behavior, then the kids
the mouse        which view is under a point; hovered / pressed; on_click

    What is DIFFERENT per kind of widget lives in its behavior (behavior.sharp): how. A view never checks "am I a button?".

    LAYOUT IN TWO PASSES (the same idea as Android, Flutter and Compose):

    1. measure(low_w, high_w, low_h, high_h) top-down the allowed range of sizes, bottom-up the answers: "inside that, I want want_w x want_h". 2. arrange(x, y, w, h) top-down: "here is your final rectangle" - the size it answered, at the place the parent chose.

    All positions are in WINDOW pixels (not relative to the parent). That makes painting and "what is under the mouse" trivial; moving a subtree (scrolling) is done by arranging it again.

    THE BOX:

    (x, y) +------------------------------+
       |  padding                     |
       |   +----------------------+   |
       |   |  content             |   |   h
       |   |  (inner_x .. inner_h)|   |
       |   +----------------------+   |
       +------------------------------+
                      w

    You normally never touch a view directly: a modifier passed to the widget (.padding(), .background(), .fill() ...) sets these fields for you (modifier.sharp).

    def measure(low_w: decimal, high_w: decimal, low_h: decimal, high_h: decimal)

    Work out want_w x want_h. The parent says how small and how big this box may be, each way:

    low_w .. high_w   and   low_h .. high_h

    high may be UNBOUNDED ("as big as you like"); low == high means "exactly this size, no choice". This pair of ranges is the whole conversation between a parent and a child. (It is Compose's Constraints: minWidth / maxWidth / minHeight / maxHeight. Android's MeasureSpec says the same with three modes: EXACTLY is low == high, AT_MOST is low 0, UNSPECIFIED is high unbounded.)

    The box's own modifiers then narrow the range, in this order, always staying inside what the parent allowed (the parent wins):

    - fill: the smallest allowed becomes the biggest allowed (when that is limited) - "exactly as big as there is room"; - min / max size; - an exact size: both ends become it.

    The behavior measures the content inside what is left after padding, and the box ends up as content + padding, pulled into the range.

    WHY THE RANGE MATTERS: because the child is told its exact size HERE when the parent already knows it (a child that shares a row's leftover room, a child that fills), it measures its content once, for the size it really gets. arrange() never has to measure again.

    Measuring a box twice with the same range in one layout pass costs nothing: the answer is remembered (Android keeps the same kind of cache in View.measure).

    class widget

    : element · source

    widget - what every built-in widget class starts from: its view.

    class label base widget : behavior { ... }

    A widget is two things joined together:

    - its VIEW (me): the one box it has in the tree (view.sharp) - position, size, padding, background, children. Every widget has one, and they are all the same class. - its BEHAVIOR: the widget class itself, which implements behavior and answers how big its content is, where its children go and what it paints (behavior.sharp).

    A widget class's constructor calls attach(self): that makes the view, tells it who to ask about content, and - when a container's block is running - puts the new widget into that container (scope.sharp).

    WHAT IS NOT HERE: settings for the box (padding, size, fill, background, click ...). Those are not widget functions at all. They are chained onto a modifier that is passed in where the widget is made (modifier.sharp), so there is exactly one way to say them and every widget understands all of them. A widget class only adds the settings that are about what it IS: a text's size and colour, a column's gap, a button's look.

    element is what containers accept as a child: anything with a view - every widget, and every composable.
