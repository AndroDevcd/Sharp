    class color

    source

    color - how much red, green and blue a thing is, and how solid it is (alpha). Every channel is 0..255; alpha 255 is fully solid, 0 is invisible.

    Like java.awt.Color or Compose's Color. Make one through the front door so your code reads in one voice:

    p.rect(10, 10, 200, 80, gui.rgb(24, 28, 40));          // solid dark blue
p.rect(10, 10, 200, 80, gui.rgba(0, 0, 0, 128));       // half see-through black

    A colour is made once and then only read, so keep the ones you use often in variables instead of making them again every frame.

    packed is all four channels in ONE whole number (0xRRGGBBAA). That single number is what crosses over to the native side on every drawing call - one argument instead of four. C++ comparison: a uint32_t RGBA colour.

    Fields

    red_int32
    green_int32
    blue_int32
    alpha_int32
    packed_int640xRRGGBBAA, worked out once here

    the same colour, more or less see-through: c.with_alpha(128)

    class event

    source

    event - one thing that happened to a window: a key, the mouse, the close button, a resize, typed text.

    kind says which (the EVENT_ list above), and only the fields that kind fills in mean anything - the rest are 0. Like an SDL_Event or an Android MotionEvent/KeyEvent rolled into one small record.

    e := w.next_event();
while(e.kind != EVENT_NONE) {
    if(e.kind == EVENT_QUIT) { w.close(); }
    if(e.kind == EVENT_KEY_DOWN && e.key == KEY_ESCAPE) { w.close(); }
    if(e.kind == EVENT_MOUSE_DOWN) { println("click at " + e.x + ", " + e.y); }
    e = w.next_event();
}

    A window keeps ONE event object and refills it on every next_event(), so reading events makes no garbage. Copy out the numbers you want to keep.

    TYPING: for text a person types, use EVENT_TEXT (it already has shift, caps lock and the keyboard layout applied). Use EVENT_KEY_DOWN for keys as buttons: arrows, escape, shortcuts.

    Fields

    kind_int64
    x_int64mouse position, in pixels from the window's top-left corner
    y_int64
    button_int64MOUSE_LEFT, MOUSE_MIDDLE, MOUSE_RIGHT
    moved_x_int64how far the mouse moved, across and down (also while the window keeps it: gui.keep_mouse)
    moved_y_int64
    key_int64which key (a character, or a KEY_ name)
    modifiers_int64MOD_SHIFT + MOD_CTRL + MOD_ALT that were held
    repeat_int641 when the key is being held and the keyboard repeats it
    wheel_x_int64wheel steps sideways
    wheel_y_int64wheel steps: more than 0 is away from you (scroll up)
    width_int64the window's new size after a resize
    height_int64
    textstringwhat was typed (EVENT_TEXT)

    Fill this event with the next one waiting on the native side (called by window.next_event). What a, b, c, d carry depends on the kind - the table is in gui/platform/native/sharpgui.cpp next to the EVT_ list.

    class font

    source

    font - a typeface at one size, ready to draw text with.

    title := gui.font(28);                       // the system's standard font, 28 pixels
mono  := gui.font("fonts/code.ttf", 14);     // your own .ttf file
    p.text("Hello", 20, 20, title, white);
wide := title.width_of("Hello");             // to centre or right-align it

    The size is in pixels, like CSS px (16 is ordinary reading text).

    Making a font the first time prepares every letter (a few milliseconds); asking for the same file and size again hands back the one already made, so calling gui.font(16) inside a draw loop is cheap. A font belongs to the open window and ends with it. Java comparison: java.awt.Font + FontMetrics in one.

    WITHOUT A WINDOW (a UI test: window.sharp, "a window that is not there") no font file is read. A font then measures by rule: every character is half the font's size wide, a line 1.3 times its size high. Text in a test is so the same size on every machine, whatever fonts it has.

    Fields

    by_rulebooltrue while the window is one that is not there: fonts measure by rule (set by window)
    id_int64the native side's number for this font (0: it measures by rule)
    sizedecimalthe size it was made at, in pixels
    line_heightdecimalpixels from one line of text down to the next

    Functions

    font(path: string, pixels: decimal)

    how many pixels wide this text is in this font (one line)

    class image

    source

    image - a picture loaded from a file (PNG, JPG, BMP, GIF), ready to draw.

    logo := gui.image("assets/logo.png");
p.image(logo, 20, 20);                       // at its own size
p.image(logo, 20, 20, 64, 64);               // stretched to 64 x 64

    Load a picture ONCE (before the frame loop) and draw it as often as you like; loading the same file again hands back the one already loaded. PNG transparency is kept. A picture belongs to the open window and ends with it. In a window that is not there (a UI test) no file is read: every picture counts as 100 x 100. Android comparison: a Bitmap; in a game: a sprite sheet or texture.

    Fields

    id_int64the native side's number for this picture
    width_int32its own size in pixels
    height_int32

    Functions

    image(path: string)
    def smooth(on: bool)

    how the picture is scaled when it is drawn larger or smaller than it is: true (how every picture starts) smoothly, right for photos and drawn art; false keeps every pixel a sharp square, which is what pixel art needs.

    class painter

    source

    painter - the thing you draw with. Shapes, lines, text and pictures.

    Get it from the window and paint between clear() and show():

    p := w.painter();
w.clear(background);
p.rect(20, 20, 200, 80, 12, card);               // a round-cornered box
p.circle(60, 60, 18, accent);
p.text("Hello", 90, 48, title_font, white);
w.show();

    HOW POSITIONS WORK: (0, 0) is the top-left corner, x grows to the right, y grows DOWN. Every shape is placed by its top-left corner and its width and height - except circles, placed by their centre. Numbers are decimals, so things can move smoothly between pixels.

    Things painted later cover things painted earlier (like real paint). Colours with alpha below 255 let what is underneath show through.

    TWO THINGS THE FRAMEWORK USES (and you may too): - clip(x, y, w, h) ... unclip(): paint only inside an area. They nest. - move_origin(x, y) ... restore_origin(): make (0, 0) mean somewhere else, so a piece of drawing code can pretend it owns the whole window. A canvas in the middle of a layout is handed a painter set up like this.

    This is the "immediate" layer: you say what to paint, every frame. Games use it directly (the canvas); the declarative layer - gui.column(), gui.button() - is built ON it and calls it for you. Java comparison: Graphics2D. Android: Canvas. HTML: the 2D canvas context.

    Fields

    silentboolA SILENT painter draws nothing: every function that would reach the screen returns at once.

    def fade(amount: decimal) : decimal

    From now on, paint everything this much more see-through: 1 changes nothing, 0.5 makes everything half as solid, 0 invisible. It multiplies with a fade that is already on, so a faded panel inside a faded screen is fainter still. Returns the level that was on before: hand it to unfade() when done.

    before := p.fade(0.5);
... paint things ...
p.unfade(before);

    This is how a widget's opacity and the fade animations work: the whole subtree is painted between a fade() and its unfade(). Every colour passes through the level on its way to the native side (ink, below), so nothing that paints needs to know it is being faded.

    class shape_batch

    source

    shape_batch - many shapes, painted with ONE call.

    shapes := new shape_batch();                // once, before the frame loop
    shapes.clear();                             // every frame: fill it again ...
shapes.rect(0, 0, 200, 80, 0x3C3F46FF);
shapes.circle(60, 60, 18, 0xFFD65AFF);
shapes.line(0, 0, 200, 80, 2, 0x000000FF);
p.draw(shapes);                             // ... and paint all of it

    WHY: every p.rect(...) crosses into the graphics side on its own, and that crossing costs far more than the rectangle - a few hundred shapes a frame is all a small machine (a Raspberry Pi) has time for. A batch only writes numbers into its lists; p.draw(batch) crosses once for all of them, and the graphics card gets them as one list too.

    The shapes are painted in the order they were added, later ones over earlier ones, exactly as separate calls would. Colours are numbers, 0xRRGGBBAA (gui.pack(r, g, b) makes one). Positions are the painter's, like p.rect's.

    A batch keeps what it holds until clear(): one that never changes (a background) can be filled once and drawn every frame.

    (In a game engine: a sprite batch or a vertex buffer. HTML canvas: a Path2D.)

    class window

    source

    Functions

    window(w: _int32, h: _int32)

    A WINDOW THAT IS NOT THERE: nothing opens on any screen and the native library is not loaded. It has a size, a clock and events like a real one, but they are whatever the program says they are:

    send(e)             an event to hand out from next_event()
pass_time(0.5)      the clock moves on by half a second
resize(w, h)        the size changes

    Painting on it paints nowhere (its painter is silent). It is what a UI test runs a screen on (std.guikit.testing): the screen is built, laid out and clicked exactly as on a real window, in no time, on a machine without a display.

    The same, opened in a mode. w and h are still the size of the window itself: what it has when it is, or goes back to being, windowed.

    enum window_mode

    source

    How a window sits on the screen.

    windowed     an ordinary window of the size it was opened with
maximized    fills the desktop; the title bar and the taskbar stay
fullscreen   the whole screen and nothing else, at the resolution the
             screen already has (a game, a kiosk on a Raspberry Pi)

    Open in a mode with gui.run("App", window_mode.fullscreen, ...), change it while the program runs with gui.set_mode(...) or gui.fullscreen(true / false). (The numbers are the ones the native side uses: MODE_* in sharpgui.cpp.)
