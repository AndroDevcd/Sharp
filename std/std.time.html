    class calendar

    source

    Calendar helpers that build on date: laying out a month for printing, finding "the 3rd Monday of the month", the date of Easter, and counting in business days. Everything is a static function; the class has no state.

    calendar.nth_weekday_of_month(2024, 11, day_of_week.thursday, 4)   // 2024-11-28 (US Thanksgiving)
calendar.easter(2024)                                              // 2024-03-31
calendar.plus_business_days(date.of(2024, 3, 1), 1)                // Friday -> Monday 2024-03-04
println(calendar.month_text(2024, 2, day_of_week.monday));

    "Business day" here means Monday to Friday. Public holidays differ by country and year and are not built in; the functions with a holidays parameter take the dates to skip from the caller.

    static def easter(year: decimal): date

    The date of Easter Sunday in the Gregorian calendar, as celebrated by the Western churches: the first Sunday after the first full moon on or after 21 March, by the church's tables.

    Algorithm: the "anonymous Gregorian algorithm" (also called the Meeus/Jones/Butcher algorithm), first printed in Nature in 1876 and given in Jean Meeus, "Astronomical Algorithms", chapter 8. With all divisions dropping their fraction:

    a = year mod 19          b = year / 100        c = year mod 100
d = b / 4                e = b mod 4           f = (b + 8) / 25
g = (b - f + 1) / 3      h = (19a + b - d - g + 15) mod 30
i = c / 4                k = c mod 4
l = (32 + 2e + 2i - h - k) mod 7
m = (a + 11h + 22l) / 451
month = (h + l - 7m + 114) / 31
day   = (h + l - 7m + 114) mod 31 + 1

    2024 -> 31 March, 2025 -> 20 April, 2000 -> 23 April, 1961 -> 2 April.

    @throws date_time_exception when year is before 1583 (the first Easter of the Gregorian calendar) or after 999,999

    static def orthodox_easter(year: decimal): date

    The date of Easter Sunday as celebrated by the Eastern Orthodox churches, given as a date of the (Gregorian) calendar this library uses. Orthodox Easter is computed in the JULIAN calendar.

    Algorithm: Meeus' Julian Easter algorithm ("Astronomical Algorithms", chapter 8):

    a = year mod 4     b = year mod 7     c = year mod 19
d = (19c + 15) mod 30
e = (2a + 4b - d + 34) mod 7
month = (d + e + 114) / 31
day   = (d + e + 114) mod 31 + 1          (a Julian calendar date)

    The Julian date is then moved to the Gregorian calendar by adding the difference between the two calendars, which is year/100 - year/400 - 2 days (13 days from 1900 to 2099).

    2024 -> 5 May, 2025 -> 20 April (the same day as Western Easter), 2016 -> 1 May.

    @throws date_time_exception when year is before 1583 or after 999,999

    static def plus_business_days(start: date, count: decimal): date

    interface clock

    source

    Something that knows what time it is.

    Code that needs the current time should ask a clock it was given instead of calling instant.now() directly. In the program the clock is system_clock.instance; in a test it is a manual_clock or fixed_clock that the test sets and advances, so the test gives the same result every time and never has to wait.

    def is_expired(c: clock, expires: instant): decimal {
    return c.now() >= expires;
}

    stopwatch, deadline, rate_limiter and interval_timer all take their time from a clock for exactly this reason.

    Implementations: system_clock, fixed_clock, manual_clock, offset_clock.

    class date

    source

    A calendar date without a time of day and without a time zone: year, month and day, e.g. 2024-02-29.

    The calendar is the PROLEPTIC GREGORIAN calendar (ISO-8601): today's leap year rule is applied to every year, also to years before the calendar was introduced in 1582, and there is a year 0 (which is 1 BC) and negative years. Years from -999,999 to 999,999 are supported.

    Dates are immutable: every "plus", "minus" or "with" returns a new date.

    Epoch days ---------- Much of the arithmetic works on the EPOCH DAY: the number of days since 1970-01-01, which is day 0 (1969-12-31 is -1, 2000-01-01 is 10957). The conversions between year/month/day and the epoch day are Howard Hinnant's days_from_civil and civil_from_days (http://howardhinnant.github.io/date_algorithms.html). They are exact whole-number formulas with no loops and no tables, valid for every year in the supported range.

    d := date.of(2024, 2, 29);
d.day_of_week()              // day_of_week.thursday
d.plus_years(1)              // 2025-02-28   (clamped to the end of the month)
d.plus_days(1).to_string()   // "2024-03-01"
d.to_epoch_day()             // 19782
date.parse("2000-01-01") < d // 1

    def iso_week(): decimal

    The ISO-8601 week number: 1 .. 53.

    ISO weeks start on Monday, and week 1 is the week that contains the first Thursday of the year (equivalently: the week with 4 January). The first days of January can therefore belong to week 52 or 53 of the year before, and the last days of December to week 1 of the next year; iso_week_year() tells which year the week belongs to.

    Formula: week = floor((day_of_year - weekday + 10) / 7) with weekday 1 = Monday .. 7 = Sunday. A result of 0 means the last week of the previous year; a result of 53 in a year that has only 52 weeks means week 1 of the next year.

    2021-01-03 -> week 53 (of 2020)      2024-12-30 -> week 1 (of 2025)

    static def of_epoch_day(epoch_day: decimal): date

    The date that is epoch_day days after 1970-01-01 (before, when negative).

    Algorithm: Howard Hinnant's civil_from_days. The calendar repeats every 400 years = 146,097 days (an "era"). Shifting the day count by 719,468 makes day 0 the 1st of March of year 0, so that the leap day is the LAST day of the (March-based) year and needs no special case:

    z = epoch_day + 719468 era = floor(z / 146097) doe = z - era * 146097 day of era 0 .. 146096 yoe = (doe - doe/1460 + doe/36524 - doe/146096) / 365 year of era 0 .. 399 doy = doe - (365*yoe + yoe/4 - yoe/100) day of the March-based year 0 .. 365 mp = (5*doy + 2) / 153 month, 0 = March .. 11 = February day = doy - (153*mp + 2)/5 + 1 month = mp < 10 ? mp + 3 : mp - 9 year = yoe + era*400, plus 1 when month is January or February (every division drops its fraction)

    @throws date_time_exception when the result is outside the supported years

    class date_time

    source

    A date together with a time of day, without a time zone: e.g. 2024-02-29T13:45:30 ("local date-time" in java.time and kotlin).

    It is what a calendar and a wall clock show somewhere, but it does not say WHERE, so on its own it is not a point on the time line. Combine it with a zone_offset (at_offset, to_instant) to get one.

    Unlike time_of_day, arithmetic here carries over midnight into the date: 2024-02-28T23:30 plus 1 hour is 2024-02-29T00:30.

    Precision: the date and the time are kept as a date and a time_of_day, so everything is exact to the nanosecond; nothing is ever stored as one big nanosecond count (which a decimal could not hold - see instant).

    Values are immutable.

    dt := date_time.of(2024, 2, 28, 23, 30, 0);
dt.plus_hours(1).to_string()                 // "2024-02-29T00:30:00"
dt.to_epoch_second(zone_offset.utc)          // 1709163000
date_time.parse("1999-12-31T23:59:59").plus_seconds(1).year()   // 2000

    class date_time_formatter

    source

    Formats dates and times as text, and parses text back, following a PATTERN such as "yyyy-MM-dd HH:mm:ss" - the pattern language of java.time.format.DateTimeFormatter / kotlin, reduced to what works without locale data (names are English).

    Pattern letters --------------- The NUMBER of letters matters: it sets the width, or chooses between a number and a name.

    y year yyyy -> 2024 yy -> 24 y -> 2024 (no padding) M month M -> 2 MM -> 02 MMM -> Feb MMMM -> February d day of month d -> 9 dd -> 09 D day of year D -> 60 DDD -> 060 E day of week, name E, EE, EEE -> Thu EEEE -> Thursday e day of week, number 1 (Monday) .. 7 (Sunday) w ISO week of the year w -> 9 ww -> 09 Y ISO week-based year YYYY -> 2024 (the year the ISO week belongs to) Q quarter 1 .. 4 H hour 0-23 H -> 7 HH -> 07 h hour 1-12 h -> 7 hh -> 07 a AM / PM m minute m -> 5 mm -> 05 s second s -> 5 ss -> 05 S fraction of second as many digits as letters: SSS -> 250 (1 to 9 letters) n nanosecond of second n -> 250000000 X offset, "Z" for UTC X -> +02 or +0530 XX -> +0200 XXX -> +02:00 x offset, never "Z" x -> +00 xx -> +0000 xxx -> +00:00 Z offset +0200 '...' literal text 'T' 'at' ('' is one quote character)

    class duration

    source

    An amount of time: "2 hours 30 minutes", "1.5 seconds", "-10 milliseconds".

    A duration is not tied to a calendar. It is a length measured in seconds, so a day is always exactly 86,400 seconds. For amounts in calendar units (months, years) use period.

    How the value is stored - and why --------------------------------- A decimal holds whole numbers exactly only up to 2^53 (about 9.0e15). In nanoseconds that is just 104 days, so a single nanosecond count cannot hold a long duration without losing its low digits. A duration therefore keeps TWO numbers, the same way java.time.Duration does:

    seconds   whole seconds, may be negative        (exact up to 2^53 s = 285 million years)
nanos     nanoseconds on top of that, 0 .. 999,999,999  (never negative)

    The value is always seconds + nanos / 1e9. A negative duration has negative seconds and a positive nano adjustment: -0.5 s is stored as seconds = -1, nanos = 500,000,000.

    Durations are immutable: every operation returns a new duration.

    d := duration.of_minutes(90) + duration.of_seconds(30);
d.to_minutes()        // 90
d.to_string()         // "1h 30m 30s"
d.to_iso_string()     // "PT1H30M30S"
duration.parse("PT1.5S") == duration.of_millis(1500)   // true

    class instant

    source

    A single point on the UTC time line, independent of any calendar or time zone - the thing a timestamp stores.

    How the value is stored - and why --------------------------------- The obvious representation, "nanoseconds since 1970", does not fit in a decimal: a decimal holds whole numbers exactly only up to 2^53 (about 9.0e15) and the present is about 1.7e18 ns after 1970, so the last digits would be rounded away (the spacing between neighbouring decimal values at that size is 256 ns). An instant therefore keeps TWO numbers, like java.time.Instant:

    epoch_second   whole seconds since 1970-01-01T00:00:00Z, negative before  (exact)
nano           nanoseconds within that second, 0 .. 999,999,999           (exact)

    All arithmetic and comparison work on the pair and are exact to the nanosecond. Only now() is limited by the runtime: vm.time_in_nanoseconds hands the system clock over as one decimal, so the reading itself is already rounded to a multiple of 256 ns (and Windows clocks tick in 100 ns steps).

    The clock behind now() is the SYSTEM clock: it can jump when the operating system corrects the time. The runtime offers no monotonic clock.

    The supported range is the range of date: years -999,999 to 999,999. Instants are immutable.

    t := instant.of_epoch_second(1709211600);
t.to_string()                                   // "2024-02-29T13:00:00Z"
(t + duration.of_hours(11)).to_string()         // "2024-03-01T00:00:00Z"
instant.parse("1970-01-01T00:00:01.5Z").to_epoch_milli()   // 1500

    class rate_limiter

    source

    Limits how often something may happen: at most permits times per window, e.g. 5 requests per second.

    It never waits and starts no thread. The caller asks try_acquire() before doing the thing; the answer is 1 ("go ahead", one permit is used up) or 0 ("not now"). time_until_available() says how long to wait.

    Algorithm: TOKEN BUCKET ----------------------- Picture a bucket that holds at most permits tokens and starts full. Each allowed action takes one token out. Tokens drip back in at a steady rate of one every window / permits (5 per second = one every 200 ms) until the bucket is full again. So a burst of up to permits actions is allowed at once, and over a long time the rate cannot exceed permits per window.

    To stay exact the bucket does not store a fractional token count. It stores how many whole tokens it has and the moment refilled_at up to which dripping has been accounted for; on each call the whole number of drip intervals since then is added and refilled_at moves forward by exactly that many intervals, so no time is lost to rounding.

    The time comes from a clock (system clock by default, a manual_clock in tests). The class is not synchronised: share it between threads only under a lock.

    limiter := new rate_limiter(5, duration.of_seconds(1));
if(limiter.try_acquire()) { send_request(); }

    class system_clock

    : clock · source

    The real clock: the operating system's time, read through the runtime's nanosecond clock (vm.time_in_nanoseconds, nanoseconds since 1970-01-01T00:00:00Z).

    Things to know about it ----------------------- - It is the SYSTEM ("wall") clock. It can jump forwards or backwards when the operating system corrects the time (NTP, a user changing the clock). The runtime has no monotonic clock, so elapsed times measured with it (stopwatch, measure_time) can occasionally be wrong by the size of such a correction, or even negative. - The runtime returns the reading as one decimal. A decimal holds whole numbers exactly only up to 2^53; the reading is about 1.7e18, where neighbouring decimal values are 256 ns apart. The reading is therefore only good to about a quarter of a microsecond. now() splits it into whole seconds and nanoseconds at once (see below) so nothing more is lost afterwards.

    Calendar arithmetic needs FLOOR division instead: the day before 1970-01-01 is day -1 and belongs to the week, month and year that came before, not to a mirrored copy of the ones after. floor_div and floor_mod round towards negative infinity:

    floor_div(-7, 3) == -3      floor_mod(-7, 3) == 2      (-3 * 3 + 2 == -7)
floor_div( 7, 3) ==  2      floor_mod( 7, 3) == 1

    All functions expect whole numbers whose size is below 2^53.

    class time_of_day

    source

    A time as shown by a wall clock, without a date and without a time zone: hour, minute, second and nanosecond, e.g. 13:45:30.5.

    Range: 00:00:00.000000000 (midnight) to 23:59:59.999999999. There is no 24:00 and no leap second (second 60).

    Arithmetic WRAPS AROUND midnight: 23:00 plus 2 hours is 01:00, and 00:10 minus 20 minutes is 23:50. Use date_time when the change of day matters. Values are immutable: every operation returns a new time.

    A time of day is at most 86,400 * 1e9 = 8.64e13 nanoseconds, far below 2^53, so the whole value fits in one decimal exactly (to_nano_of_day).

    t := time_of_day.of(13, 45, 30);
t.plus_hours(12)            // 01:45:30
t.to_second_of_day()        // 49530
t.to_string()               // "13:45:30"
time_of_day.parse("07:05:00.250").nano()   // 250000000

    class zone_offset

    source

    A fixed difference from UTC, such as +02:00 or -05:30.

    The offset is how far a local clock is AHEAD of UTC: at offset +02:00 a local clock shows 14:00 when it is 12:00 UTC. Offsets from -18:00 to +18:00 are accepted (the same limit java.time uses), with a resolution of one second.

    LIMITATION: the runtime has no time-zone database, so there are no named zones ("Europe/Berlin") and no daylight saving rules. An offset is just a constant number of seconds. zone_offset.system_default() gives the offset the operating system uses right now, which is correct for the current moment but not necessarily for dates in another season.

    Offsets are immutable.

    plus2 := zone_offset.of_hours(2);
plus2.to_string()                      // "+02:00"
zone_offset.parse("-05:30").total_seconds()   // -19800
zone_offset.utc.to_string()            // "Z"
