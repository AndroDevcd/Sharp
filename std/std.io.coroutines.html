    class async<t>

    source

    async<t> - start a coroutine that computes a value; the result is a deferred<t>.

    USAGE price := async<int>.start({ -> (int) return fetch_price(); }); stock := async<int>.start(warehouse, { w: object -> (int) house := w as storage; // the state object, see THE CLOSURE RULE return house.count(); }); println("worth ${price.await() * stock.await()}");

    The language has no generic functions, so async is a class whose static functions do the work: write the result type once, async<int>.start(...).

    The block runs on another fiber: THE CLOSURE RULE (builders.sharp) applies, no captured locals. The new coroutine is a child of the current coroutine or scope (of global_scope outside any), exactly like launch.

    FAILURES: the exception of the block is thrown by await(). As in Kotlin it ALSO cancels the parent scope, unless that is a supervisor (supervisor_scope, global_scope).

    t must be an object type: async<int>, not async<decimal>.

    Kotlin equivalent: async { }. C++ equivalent: std::async on a fiber.

    No state, so nothing to lock.

    class cancellation_exception

    base exception · source

    cancellation_exception - thrown inside a coroutine at a cancellation point after its job was cancelled.

    USAGE j := launch({ -> try { delay(10000); // a cancellation point } catch(e: cancellation_exception) { println("cancelled, cleaning up"); throw e; // let the coroutine end as cancelled } }); j.cancel();

    Cancellation is cooperative: nothing stops a coroutine by force. The cancellation points are delay(), yield(), ensure_active(), job.join(), deferred.await(), every channel operation, mutex.acquire() and semaphore.acquire(). A coroutine that never reaches one of them runs to its end even when it is cancelled.

    A coroutine that ends with a cancellation_exception counts as CANCELLED, not as failed: its parent is not cancelled and nothing is reported as an error. Catching it without throwing it again is allowed but makes the coroutine carry on although it is cancelled; the next cancellation point throws again.

    Kotlin equivalent: kotlinx.coroutines.CancellationException. Java equivalent: java.util.concurrent.CancellationException.

    interface coroutine_body

    source

    coroutine_body - the code a coroutine runs.

    USAGE class download : coroutine_body { url : string; download(url: string) { self->url = url; } override def run_body() { fetch(url); } }

    launch(new download("http://..."));      // an object instead of a lambda

    WHY IT EXISTS 1. A lambda that runs on another fiber cannot see the local variables of the function that created it (see builders.sharp, "THE CLOSURE RULE"). An object that implements coroutine_body carries its own data in its fields, which is the cleanest way to hand state to a coroutine. 2. Methods are only dispatched at run time through an interface reference. job calls run_body() through this interface, which is what lets deferred<t> replace it with a version that keeps the result.

    Kotlin equivalent: the block: suspend CoroutineScope.() -> Unit parameter of launch. Java equivalent: java.lang.Runnable.

    run_body() may suspend (delay, join, channel operations, ...) and may throw: the exception ends the coroutine and is handled by its job.

    interface coroutine_dispatcher

    source

    coroutine_dispatcher - decides which thread runs a coroutine.

    USAGE launch_on(dispatchers.default_pool(), { -> crunch(); }); // any worker thread ui := dispatchers.single_thread("ui"); launch_on(ui, { -> draw(); }); // always the "ui" thread

    The runtime knows two kinds of fibers and a dispatcher simply picks one: select_thread() returns null an UNBOUND fiber: whichever thread is free takes it (and it may continue on another thread after it has slept) select_thread() returns a thread a fiber BOUND to that thread: only that thread ever runs it

    A coroutine started without a dispatcher uses the one of its parent.

    Kotlin equivalent: kotlinx.coroutines.CoroutineDispatcher (reduced to the one decision this runtime offers). Java equivalent: java.util.concurrent.Executor.

    select_thread() is called once per coroutine, by the fiber that starts it. It must not block for long and must be safe to call from several threads.

    interface coroutine_exception_handler

    source

    coroutine_exception_handler - what happens to an exception nobody is left to receive: a coroutine started with launch() directly in global_scope (or in a supervisor) ended with an exception that is not a cancellation.

    USAGE class log_errors : coroutine_exception_handler { override def handle_exception(failed: job, error: throwable) { println("coroutine failed: ${error.get_message()}"); } }

    coroutine_exceptions.set_handler(new log_errors());

    The handler runs in the fiber that finished the failed coroutine: keep it short, do not block in it, and do not throw from it (an exception thrown by the handler is dropped).

    Kotlin equivalent: kotlinx.coroutines.CoroutineExceptionHandler. Java equivalent: Thread.UncaughtExceptionHandler.

    class coroutine_exceptions

    source

    coroutine_exceptions - where uncaught coroutine exceptions go.

    USAGE coroutine_exceptions.set_handler(my_handler); // see coroutine_exception_handler coroutine_exceptions.set_handler(null); // back to printing them coroutine_exceptions.count(); // how many were reported so far

    WHICH EXCEPTIONS END UP HERE - launch() in global_scope or in a supervisor (supervisor_scope { }, coroutine_scope.supervisor()) and the coroutine throws: reported here. - launch() inside coroutine_scope { } / run_blocking { } / another coroutine: NOT reported here. The failure cancels the parent and is thrown again by the enclosing scope function. - async: never reported here, deferred.await() throws it. - cancellation_exception: never reported, being cancelled is not an error.

    Without a handler the exception is printed, like an uncaught exception of a thread. Kotlin equivalent: the default handler that calls Thread.uncaughtExceptionHandler.

    The handler is called on a fiber of its own, never inside the library code that noticed the failure (that code must not have user code on its stack, see NO RECURSION in job.sharp).

    LOCKING DISCIPLINE: guard protects handler and reported. The handler is called after the lock is released.

    class coroutine_scope

    source

    coroutine_scope - an object that owns coroutines, so that they can be cancelled and waited for as a unit. Give one to everything that has a life time: a connection, a window, a request.

    USAGE class connection { scope := new coroutine_scope();

    def open() {
    scope.launch(self, { s: object -> c := s as connection; c.read_loop(); });
    scope.launch(self, { s: object -> c := s as connection; c.ping_loop(); });
}
        def close() {
        scope.cancel_and_join();         // both loops have stopped when this returns
    }
}

    A failing coroutine cancels the scope and with it all the others, unless the scope was made with coroutine_scope.supervisor(). The scope's own job has no code: it is active until cancel() or complete() is called.

    The coroutines run on other fibers: THE CLOSURE RULE (builders.sharp) applies to the blocks handed to launch().

    Kotlin equivalent: CoroutineScope(Job() + dispatcher) / CoroutineScope(SupervisorJob()). (The function coroutine_scope { } in scopes.sharp is Kotlin's coroutineScope { }.)

    LOCKING DISCIPLINE: the only state is the job, which locks itself.

    class deferred<t>

    base job · source

    deferred<t> - a job that produces a value: the result of async.

    USAGE a := async<int>.start({ -> (int) return slow_sum(); }); b := async<int>.start({ -> (int) return slow_product(); }); total := a.await() + b.await(); // both ran at the same time

    all := deferred<int>.await_all(new deferred<int>[] { a, b });   // a list<int>

    A deferred IS a job: join(), cancel(), is_active() and the rest work as for any coroutine. Its exception is not reported as uncaught; await() throws it.

    t must be an object type (int, string, your classes ...): deferred<decimal> and other native numbers are not supported, write deferred<int>.

    Kotlin equivalent: kotlinx.coroutines.Deferred<T>. C++ equivalent: std::future<T> whose get() suspends a fiber instead of blocking a thread. Java equivalent: CompletableFuture<T>.

    LOCKING DISCIPLINE: see job. result is written by the fiber of the coroutine before the job reaches its final state and read by others only after they have seen the final state (join returned), so it needs no lock of its own.

    interface holding_dispatcher

    source

    holding_dispatcher - what a dispatcher ALSO is when it KEEPS the coroutines it is given instead of letting them start: they start when it says so. A class implements both: class my_dispatcher : coroutine_dispatcher, holding_dispatcher.

    It is what a test dispatcher is (std.guikit.testing: test_dispatcher()): the work a model starts must not run until the test asks for it, and then in the order it was started. An ordinary dispatcher only picks a thread; it cannot stop a coroutine from starting - on a thread that is busy too, the runtime gives a waiting fiber its turn sooner or later.

    start_coroutine (builders.sharp) hands every coroutine placed on a holding_dispatcher to hold() and does not start it. Whoever holds it calls start_held(coroutine) later; select_thread() then says where it runs, as for any dispatcher. A coroutine started INSIDE held work, without a dispatcher of its own, takes its parent's - so it is held too.

    Kotlin equivalent: StandardTestDispatcher, whose scheduler keeps the tasks until advanceUntilIdle() / runCurrent().

    class job

    : coroutine_body · source

    job - the handle of one coroutine (or of a scope that owns coroutines): ask what it is doing, wait for it, cancel it.

    USAGE j := launch({ -> do_work(); }); j.is_active(); // true until the work and all its children are done j.join(); // suspends the caller until then j.cancel(); // asks it to stop (cooperative, see cancellation_exception) j.cancel_and_join(); // cancel, then wait until it really has stopped j.invoke_on_completion({ done: job -> println("finished: ${done.is_cancelled()}"); });

    Kotlin equivalent: kotlinx.coroutines.Job. C++ has no direct equivalent (the closest is a std::jthread with its stop_token, for a fiber instead of a thread).

    LIFE CYCLE ACTIVE ------> COMPLETING ------> COMPLETED | (body done, | (all children done) | children run) | +------------------+---> CANCELLING ------> CANCELLED cancel() or a failure (body and all children done)

    state        is_active   is_completed   is_cancelled
ACTIVE         true         false          false
COMPLETING     true         false          false
CANCELLING     false        false          true
COMPLETED      false        true           false
CANCELLED      false        true           true

    PARENTS AND CHILDREN (structured concurrency) - a job started inside a coroutine or a scope is a CHILD of it - a parent is not complete before all its children are - cancelling a parent cancels all its children - a child that FAILS (ends with an exception that is not a cancellation_exception) cancels its parent, and with it its siblings, unless the parent is a supervisor (supervisor_scope, global_scope) - a child that was merely cancelled does not affect its parent

    LOCKING DISCIPLINE Every job is given one of the shared lock objects of lock_stripes (lk) when it is created. guarded by this job's lk: state, cancel_flag, body_done, failure, failed, waiting, joiners, handlers, first_child, n_children, and the hand-over fields out_kids, out_sleeper, out_joiners, out_handlers (written under the lock by the one fiber that made the state change, read by that same fiber right after it released the lock) guarded by the PARENT's lk: next_sibling, prev_sibling written once before the job is started, read only afterwards: parent, attached, supervisor, scoped, has_body, quiet, dispatcher, block0, block1, arg, body, fib state, cancel_flag and failed are also READ without the lock (one number each): the answer can be out of date by the time it is used, which is all a predicate like is_active() can promise anyway. cancel_flag only ever goes from 0 to 1. RULES: no second lock is ever taken while lk is held (two jobs may share a stripe, see lock_stripes), nothing that can throw and no user code runs inside a lock block (an exception that leaves a lock block does not release the lock).

    NO RECURSION The runtime cannot continue a fiber that was switched out while one function was on its call stack twice (known bug, see tests/suite/known_bugs/lib_coroutines_recursive_suspend.sharp). A job tree is therefore never walked by recursion: cancelling downwards and finishing upwards are both done by ONE loop with a work list (settle()). For the same reason completion handlers never run inside that loop: they get a fiber of their own, so whatever they call starts on a fresh stack.

    Suspends: join(), cancel_and_join(). Everything else returns at once.

    Fields

    ACTIVEdecimalthe body is running, or has not started yet
    COMPLETINGdecimalthe body is finished, children are still running
    CANCELLINGdecimalcancelled or failed; waiting for the body and the children to stop
    COMPLETEDdecimalfinished normally (final)
    CANCELLEDdecimalfinished after a cancellation or a failure (final)

    class pool_dispatcher

    : coroutine_dispatcher · source

    pool_dispatcher - runs coroutines on whichever worker thread is free. dispatchers.default_pool() is the one shared instance.

    USAGE dispatchers.set_parallelism(4); // optional, before the first coroutine launch_on(dispatchers.default_pool(), { -> crunch(); });

    HOW IT WORKS Coroutines are started as unbound fibers. The scheduler of the runtime hands an unbound fiber to any thread that has nothing to run, so all this class has to do is make sure such threads exist: the first coroutine starts parallelism worker threads whose own first fiber just sleeps. A thread that is blocked in run_blocking { } or job.join() helps as well, it is free while it waits. Idle workers are parked by the scheduler and cost no cpu.

    The workers are never stopped; they end with the program (the virtual machine does not wait for them when main returns).

    AUTOMATIC SIZE Without set_parallelism() the pool has one worker per cpu core minus one (the main thread works too while it waits), but at most 4. The limit is deliberate caution about the current runtime: starting a thread hangs once in a long while (seen about once in 50 program runs that started 15 threads, with every thread idle and only the first few workers created), and code that the JIT compiles while several threads are inside it can crash (tests/suite/known_bugs/lib_coroutines_jit_fiber_frames.sharp). Fewer threads means fewer chances for both. Ask for more with dispatchers.set_parallelism(n) when you need them.

    Kotlin equivalent: Dispatchers.Default. Java equivalent: Executors.newWorkStealingPool().

    LOCKING DISCIPLINE: guard protects started and parallelism. The threads are created after the lock is released, by the one caller that changed started from 0 to 1.

    class thread_dispatcher

    : coroutine_dispatcher · source

    thread_dispatcher - runs every coroutine on one particular thread.

    USAGE db := dispatchers.single_thread("database"); // a new thread of its own launch_on(db, { -> run_query(); }); // never two of these at the same time db.close(); // when it is no longer needed

    here := dispatchers.current_thread();            // the thread that is running right now

    Coroutines of one thread_dispatcher never run in parallel with each other, so state that only they touch needs no lock (they still interleave at suspension points). Each is a fiber bound to the thread, and runs when the thread is free: for a thread you created yourself that means "while its current fiber is suspended" (delay, join, run_blocking, ...).

    Kotlin equivalents: newSingleThreadContext(name), and the event loop of runBlocking for current_thread().

    class timeout_cancellation_exception

    def await_waiter(w: waiter, ms: decimal) : decimal

    Sleep on w until it is claimed - THE way a blocking operation of the library waits, because it makes the wait a cancellation point: the current job remembers the waiter and job.cancel() claims it with waiter.CANCELLED.

    The waiter must already be published (queued in the resource, under its guard) and the caller must hold no lock.

    @param ms a time limit in milliseconds, or a negative number for none @return the waiter's final state: waiter.RESUMED, CANCELLED, TIMED_OUT or CLOSED.     SUSPENDS. Never throws by itself. Outside a coroutine it is a plain park()/park_for(). Kotlin equivalent: suspendCancellableCoroutine { }
