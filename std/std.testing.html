    class mock

    source

    MOCKS - stand-ins that do no real work, remember how they were used, and give back what a test tells them to.

    store := mock<note_store>();                        // the compiler writes the class
    given { store.load(); }.returns(one_note());        // set up: what a call gives back
    book := notebook(store);                            // act
book.add("milk");
    verify { store.save("milk"); }.once();              // check: how it was used
verify { store.remove("milk"); }.never();

    ------------------------------------------------------------------------ mock<t>() ------------------------------------------------------------------------ A built-in, like get<t>(): the compiler writes a class that implements the interface t - every function of it - and makes one. Nothing to write.

    notebook(mock<note_store>())            just to fill a parameter: no set-up at all

    A FUNCTION NOBODY SET UP still works: it notes the call and gives back

    a number                0
a text                  ""
a list / hash_map       an empty one
something that may be null (`task?`)    null
nothing (no result)     nothing

    Only a function that must give back some other object has no harmless answer; calling it without a given { } fails the test and says which given to write.

    ONLY IN TESTS. mock<t>(), given { } and verify { } work inside a tests("...") { ... } group - in one of its tests, or beside them as set-up. Anywhere else (the program's own code) they throw an illegal_state_exception: a mock silently answers 0 and "", which a running program must never get by mistake.

    t must be an INTERFACE. An ordinary class's functions have bodies, and a function with a body cannot be replaced in Sharp - so the edges of a program that tests want to stand in for are written as interfaces.

    ------------------------------------------------------------------------ given { ONE CALL }.returns(value) ------------------------------------------------------------------------ The block makes the very call you mean - a real call, so the compiler checks the function's name and its arguments. Inside the block the mock does not act: it only notes WHICH call was made.

    given { store.find("milk"); }.returns(1);               for that argument
given { store.find(any_text()); }.returns(0);           for any text there
given { store.rename("a", "b"); }.with_any_arguments().returns(1);
given { store.load(); }.throws(io_exception("disk is full"));

    The block must make exactly ONE call on a mock. None, or more than one, is an error that lists what was found - so it is never a guess which call the .returns belongs to. Other code in the block (building an argument, a chain on the result) is fine: only calls ON A MOCK count. When several givens fit a call, the one written last wins.

    ------------------------------------------------------------------------ verify { ONE CALL }.once() / .times(n) / .never() / .at_least(n) ------------------------------------------------------------------------ How often was that call made? Arguments are compared as in given. verify_nothing_else(store) fails if the mock was asked anything no verify has covered.

    (Mockito: mock(), given(x).willReturn(y), verify(mock).call(). MockK: mockk(relaxed = true), every { } returns, verify { }. The block form is MockK's; "works without set-up" is Mockito's default.)

    ------------------------------------------------------------------------ A stand-in for ONE TEST: provide<t>() { ... } ------------------------------------------------------------------------ provide<note_store>() { return store; }; Wherever the program asks for a t through a replaceable<t>() definition (std.di), it gets this object, until the test ends.

    ------------------------------------------------------------------------ A mock class written by hand ------------------------------------------------------------------------ Still possible, for a stand-in with some behaviour of its own: a class on top of mock whose functions call called("name", argument) or answer("name"). mock<t>() makes exactly such a class for you.

    class test_run

    source

    TESTING - small programs that check that your code does what you meant.

    import ( std.testing )
    def main() {
    tests("a shopping basket") {
        test("a new basket is empty") {
            b := basket();
            expect(b.count()).should_be(0);
        };
    test("adding an item puts it in the basket") {
    b := basket();
    b.add("milk");
    expect(b.count()).should_be(1);
    expect(b.at(0)).should_be("milk");
};
        test("taking from an empty basket is refused") {
        b := basket();
        expect_throws<illegal_state_exception>() { b.take(); };
    };
};
        finish_tests();
}

    THE WORDS

    tests(name) { ... }         a group of tests that belong together
test(name) { ... }          one test: one thing the code should do, said as a sentence
expect(value).should_be(...)       a check. When it does not hold, the test fails THERE and the
                            rest of that test is skipped (expect.sharp lists the checks)
expect_throws<e>() { ... }    the block must throw an exception of class e
provide<t>() { ... }        for this test, the program gets this object wherever it asks for a t
mock, verify(...)           a stand-in that remembers how it was used (both: mock.sharp)
before_each { ... }         run before every test of the group (make what each test needs)
after_each { ... }          run after every test of the group, also when it failed (clean up)
show_only_failures()        say nothing about tests that pass (for a program with thousands of them)
finish_tests()              print the summary and end the program: exit code 0 when every
                            test passed, 1 when any failed (so a build script can tell)

    IN AN EDITOR. A test program started with the argument -ide-tests (sharp basket_tests -ide-tests) reports for a program instead of a person: one line for each group and test as it starts and ends, in the form editors' test views read (JetBrains "service messages"). The CLion plugin starts test programs this way and shows the groups, their tests, which failed and where each one is written. The test program itself is not changed for it.

    ONLY SOME OF THEM. -test-only <which> runs a part of the tests and passes the rest by without a word: a group by its name, or one test as "<group> > <test>". It may be given several times.

    sharp basket_tests -test-only "a shopping basket"
sharp basket_tests -test-only "a shopping basket > a new basket is empty"

    ONE TEST, ONE THING. Each test builds what it needs from scratch, does one thing, and checks the result. Tests do not share objects and do not depend on the order they run in - then a failing test points at exactly one thing.

    WHAT A FAILURE LOOKS LIKE

    a shopping basket
  ok    a new basket is empty
  FAIL  adding an item puts it in the basket
        expected 1
        but was  2
    1 failed, 1 passed (2 tests)

    A test also fails when something in it throws an exception it did not expect; the report then says which exception, its message, and where it was thrown.

    (JUnit: @Test, assertEquals, assertThrows, @BeforeEach. Kotest and Jest: describe / it / expect - whose shape this follows.)

    HOW IT WORKS: tests(...) runs its block straight away; every test(...) in it runs straight away too, inside a try. A check that does not hold throws a test_failure; test(...) catches it (and anything else thrown) and writes the failure down. Nothing is collected first and run later - what you read from top to bottom is what happens.
